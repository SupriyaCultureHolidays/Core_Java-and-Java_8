ক্লায়েন্ট-সার্ভার আর্কিটেকচার ও HTTP প্রোটোকল

Spring Framework বোঝার আগে একদম বেসিক প্রশ্ন থেকে শুরু করা দরকার — আমরা যখন ব্রাউজারে একটা ওয়েবসাইটের URL (যেমন www.amazon.com) দিই, তখন পেছনে আসলে কী ঘটে? এটাই হলো client-server architecture এর মূল আইডিয়া।

যে request পাঠায় তাকে বলা হয় client, আর যে সেই request গ্রহণ করে প্রসেস করে response ফেরত পাঠায় তাকে বলা হয় server। সহজ কথায়, server আসলে একটা কম্পিউটার যেখানে অ্যাপ্লিকেশন hosted থাকে। client কিন্তু শুধু ব্রাউজার নয় — এটা mobile app, React frontend, Postman, এমনকি অন্য একটা server-ও হতে পারে (যেমন microservice architecture-এ এক service অন্য service-কে call করলে, সেই কলার নিজেও client হয়ে যায়)।

Browser (Client) ──── HTTP Request ────► Amazon Server ◄──── HTTP Response ────

Client আর server যেন একে অপরের সাথে গুছিয়ে কথা বলতে পারে, তার জন্য দরকার একটা কমন ভাষা বা ফরম্যাট — এটাই হলো HTTP (HyperText Transfer Protocol)। এটা একটা rule book, যা ঠিক করে দেয় request-এর structure কেমন হবে, response-এর structure কেমন হবে। ডিফল্টভাবে HTTP-তে ডেটা এনক্রিপ্ট করা থাকে না, তাই সেটাকে secure করার জন্য এসেছে HTTPS (S = Secured) — যেখানে client ও server-এর মধ্যে যাওয়া-আসা সব ডেটা এনক্রিপ্টেড থাকে, যাতে মাঝপথে কেউ শুনে (listen) ফেলতে না পারে।

খেয়াল রাখো: HTTP request-এ বিভিন্ন operation বোঝানোর জন্য আলাদা আলাদা method থাকে — GET (তথ্য পড়া/retrieve), POST (নতুন তথ্য store করা), PUT (আপডেট করা), DELETE (মুছে ফেলা), PATCH (নির্দিষ্ট অংশ আপডেট করা)।

একটা পূর্ণাঙ্গ HTTP request-এর মূলত চারটা অংশ থাকে:

  • Method — কোন ধরনের কল করা হয়েছে (GET/POST/PUT/DELETE/PATCH)।
  • URL / Endpoint (Path) — কোন হোস্টের কোন নির্দিষ্ট রিসোর্সে request যাচ্ছে (যেমন www.codermy.in/courses)।
  • Headers — key-value আকারে extra মেটাডেটা, যেমন Accept: application/json (কোন ফরম্যাটে response চাই) বা authentication তথ্য।
  • Body — বিস্তারিত ডেটা, যেমন login করার সময় email আর password পাঠানো (এটা সাধারণত POST-জাতীয় call-এই থাকে, শুধু data retrieve করা GET call-এ body লাগে না)।

একইভাবে server-এর response-ও নির্দিষ্ট structure মেনে চলে — এতে থাকে status code (যেমন 200 OK মানে সফল, 201 মানে resource তৈরি হয়েছে, 404 মানে resource পাওয়া যায়নি, 500 মানে internal server error), তারপর headers এবং body।

কোর জাভা দিয়ে ওয়েব সার্ভার বানানোর চেষ্টা — সমস্যাগুলো

এখন পর্যন্ত আমরা Core Java জানি — class, object, method লেখা জানি। প্রশ্ন হলো, একটা /courses endpoint-এ হিট করলে ভেতরে কোনো না কোনো java method-ই তো call হচ্ছে। কিন্তু normal java program run হয়ে instructions execute করে exit করে যায় — অথচ একটা website 24/7 চালু থাকে, কখনো exit করে না। এটাই প্রথম পার্থক্য: website একটা প্রোগ্রাম যা একবার চলে exit করে না, বরং কন্টিনিউয়াসলি চলতে থাকে এবং request-এর জন্য অপেক্ষা করে।

Core Java-তে নেটওয়ার্কিং করার সুবিধা আছে — java.net প্যাকেজ (Java 1 থেকেই আছে), যেখানে ServerSocket-এর মতো ক্লাস দিয়ে একটা নির্দিষ্ট port-এ (যেমন 8080) incoming request শোনা (listen) যায়। একটা কম্পিউটারে একসাথে অনেক অ্যাপ্লিকেশন চলে (WhatsApp, Chrome, Spotify...), তাই কোন request কোন অ্যাপ্লিকেশনের জন্য এসেছে তা বোঝাতেই port number ব্যবহার হয়।

মূল সমস্যা: java.net দিয়ে raw bytes পড়া গেলেও, জাভার কোড HTTP ফরম্যাট বোঝে না। ওর কাছে সেটা শুধুই একটা stream of bytes — GET, endpoint, host — কোনো কিছুর মানেই সে জানে না।

ফলে ServerSocket ব্যবহার করলে ডেভেলপারকে সবকিছু ম্যানুয়ালি করতে হতো:

  • Input stream read করা (BufferedReader দিয়ে)।
  • Request ম্যানুয়ালি parse করা — method, endpoint, host আলাদা করে বের করা।
  • if/else দিয়ে নিজে থেকে endpoint অনুযায়ী সঠিক method call করা (map a method to an endpoint)।
  • Method-এর রিটার্ন থেকে ম্যানুয়ালি HTTP response তৈরি করা।
  • একসাথে একাধিক ইউজারকে সামলাতে নিজে থেকে multi-threading implement করা (নাহলে একটা request-এর কাজ চলাকালীন অন্য request আটকে থাকবে)।

এই বিপুল পরিমাণ boilerplate code-ই ছিল আসল সমস্যা — প্রতিটা ওয়েব অ্যাপ্লিকেশনে ডেভেলপারকে এই একই কাজ বারবার করতে হতো।

Servlet ও Servlet Container — বয়লারপ্লেটের সমাধান

এই ম্যানুয়াল কাজের সমাধান হিসেবে ১৯৯৭ সালে (Java Enterprise Edition-এর অংশ হিসেবে) এলো Servlet ও Servlet Container — java-তে web development-এর জন্য তৈরি প্রথম প্যাকেজ।

Servlet আসলে একটা সাধারণ java class, যেটা রান হয় একটা Servlet Container-এর ভেতরে। এই Servlet Container-কেই সাধারণত আমরা "server" বলি — এর মধ্যে সবচেয়ে জনপ্রিয় হলো Tomcat (এছাড়া আছে Jetty, Undertow)।

Tomcat-এর মতো servlet container আগের সব boilerplate কাজ নিজে করে দেয়:

  • Port ওপেন রাখা এবং incoming bytes read করা।
  • সেই raw bytes-কে HTTP request-এ decode/convert করা।
  • URL অনুযায়ী ঠিক করা কোন servlet-কে call করতে হবে (routing)।
  • Multi-threading নিজে থেকে handle করা।
  • Servlet-এর response থেকে প্রপার HTTP response বানিয়ে client-কে ফেরত পাঠানো।
Client ──HTTP Request──► Tomcat (Servlet Container) ──HttpServletRequest──► Servlet Client ◄──HTTP Response── Tomcat (Servlet Container) ◄──HttpServletResponse── Servlet

ফলে ডেভেলপার হিসেবে এখন শুধু নিজের business logic-টুকু servlet-এর ভেতরে লিখলেই হয় — port খোলা, byte parse করা, thread manage করার ঝামেলা আর নিতে হয় না। Tomcat সবসময় চালু থাকে, ঠিক অন্য যেকোনো ওয়েবসাইটের মতো, এবং request এলেই উপযুক্ত servlet-কে ডেকে দেয়।

4

Spring Framework কেন এলো — ইকোসিস্টেম ও কোর্স রোডম্যাপ

Servlet দিয়ে সমস্যা সমাধান হলেও, যখন অ্যাপ্লিকেশন বড় হয়ে enterprise-level স্কেলে পৌঁছায়, তখন servlet-oriented কোড খুবই tightly coupled হয়ে যায় — অর্থাৎ প্রচুর object আপসে interlinked হয়ে যায়, ফলে অ্যাপ্লিকেশন স্কেল করা কঠিন হয়ে পড়ে। এই সমস্যা সমাধানের জন্যই এলো Spring Framework, যা নিজস্ব কিছু core concept নিয়ে এলো — যেমন Dependency Injection ও Inversion of Control (IoC) — যা অ্যাপ্লিকেশনকে loosely coupled বানিয়ে স্কেল করা সহজ করে দেয়।

Spring-কে শুধু একটা "framework" বলাটা ঠিক না — এটা আসলে একটা পুরো ecosystem, যার ভেতরে অনেকগুলো আলাদা framework/module আছে। শুধু web application-ই নয়, Spring দিয়ে microservices, reactive applications, cloud applications, event-driven system, serverless architecture, batch processing — সবকিছু বানানো যায়।

Spring Bootউপরের সব module-এর উপর একটা automation/opinionated layer — দ্রুত project setup ও development শুরু করার জন্য
খেয়াল রাখো: Spring Boot কিন্তু Spring Framework-কে replace করেনি, এবং Spring Boot নিজে কোনো "স্কিল" নয়। এটা একটা opinionated system — কিছু default configuration ধরে নিয়ে দ্রুত project বুট-আপ করিয়ে দেয়। কিন্তু ভেতরে Spring MVC, Spring Data, Spring AOP, Spring Security-র কোর টেকনোলজি একই থাকে — শুধু Spring Boot শিখে, বাকিগুলো না শিখে কেউ পুরোপুরি Spring জানে না।

Database connectivity-র লেয়ারটাও একটা চেইন হিসেবে বোঝা দরকার: Spring Data JPA → এই আইডিয়াটা বাস্তবে implement করে Hibernate → আর Hibernate ভেতরে ব্যবহার করে JDBC (Java Database Connectivity)-কে, যেটা দিয়ে আগে সরাসরি SQL query লিখতে হতো। অর্থাৎ JPA একটা spec/rule book মাত্র, তার আসল implementation Hibernate, আর Hibernate-এর নিচেও শেষমেশ JDBC-ই কাজ করে।

Client ──► Spring Boot Application │ (Spring MVC, Spring Security, Spring AOP — সব Spring Core ভিত্তিক) ▼ Spring Data JPA ──► Hibernate ──► JDBC ──► Database

শেষে একটা গুরুত্বপূর্ণ ডিজাইন প্রশ্ন — microservices vs monolithic। মাইক্রোসার্ভিস কোনো আলাদা Spring module না, এটা একটা architecture design: হয় গোটা অ্যাপ্লিকেশন একটাই (monolithic) সব endpoint handle করে, অথবা কাজ ভাগ করে একাধিক ছোট ছোট service (যেমন Order Service, Payment Service, User Service) বানানো হয় যারা একে অপরকে HTTP call করে কথা বলে। এই পুরো architecture — Client → Spring Boot → (MVC/Security/AOP/Data, সব Spring Core-ভিত্তিক) → JPA → Hibernate → JDBC → Database — বুঝে ফেললেই একজনকে সত্যিকারের Java Full Stack Developer বলা যায়, এবং পুরো কোর্সের লক্ষ্যও এটাই।

অনুশীলন প্রশ্ন
  1. Client ও Server-এর সংজ্ঞা নিজের ভাষায় লেখো, এবং একটা উদাহরণ দাও যেখানে একটা server নিজেই আরেকটা server-এর client হয়ে যায়।
  2. HTTP request-এর চারটা অংশ কী কী? Servlet Container (যেমন Tomcat) কোন কোন কাজ ডেভেলপারের হাত থেকে সরিয়ে নেয়?
  3. Spring Boot, Spring MVC-কে replace করেনি কেন? এবং Spring Data JPA → Hibernate → JDBC — এই চেইনটা নিজের ভাষায় ব্যাখ্যা করো।

ব্রাউজার থেকে Server পর্যন্ত: Client-Server, IP, Port ও localhost

এই লেকচারে লক্ষ্য খুব সিম্পল: ব্রাউজারে একটা URL টাইপ করব আর স্ক্রিনে "Hello World" দেখব। কিন্তু কোড লেখার আগে বোঝা দরকার আসলে request-টা কোন পথ ধরে সার্ভার পর্যন্ত পৌঁছায়। আমাদের ক্ষেত্রে client হলো নিজেদের ব্রাউজার (যেমন Chrome), আর server হলো আমাদের নিজের কম্পিউটারে চলা Spring Boot অ্যাপ্লিকেশন।

বাস্তবে যখন কেউ কোনো ওয়েবসাইট (যেমন codermy.in) হিট করে, তখন প্রথমে ব্রাউজার DNS-এর কাছে গিয়ে সেই domain name-এর জন্য একটা IP address খুঁজে বের করে, কারণ প্রতিটা ডিভাইসের নিজস্ব একটা ইউনিক IP address থাকে। তারপর সেই IP address ব্যবহার করে আসল request সার্ভারে পাঠানো হয়।

এখন প্রশ্ন হলো — একই IP address-এ তো একটা কম্পিউটারে অনেকগুলো অ্যাপ্লিকেশন (Chrome, WhatsApp, Spotify, আমাদের Spring Boot app) একসাথে চলতে পারে। তাহলে অপারেটিং সিস্টেম কীভাবে বুঝবে কোন ডেটা কোন অ্যাপ্লিকেশনের জন্য? এখানেই কাজে লাগে port number। একটা IP address-এ একাধিক port থাকতে পারে, আর প্রতিটা port-এ একটা করে আলাদা অ্যাপ্লিকেশন চলে।

খেয়াল রাখো: HTTP-এর ট্রাফিক by-default port 80-তে যায়, আর HTTPS-এর ট্রাফিক port 443-এ যায়। কিন্তু বাস্তবে সার্ভারের ভেতরের অ্যাপ্লিকেশন (যেমন Spring Boot) হয়তো port 8080-এ চলছে — তখন একটা reverse proxy 443/80-এর incoming request-কে 8080-এ ম্যাপ করে দেয়।

যখন client এবং server দুটোই আমাদের নিজের কম্পিউটার, তখন আলাদা কোনো IP address লাগে না — তার বদলে একটা বিশেষ, ফিক্সড address ব্যবহার হয়: 127.0.0.1, যাকে সহজে localhost নামে লেখা যায়। এর মানে হলো "নিজেকেই request পাঠানো"। তাই আমাদের URL হবে localhost:8080/hello — এখানে 8080 হলো port number আর /hello হলো সেই API endpoint যেটা আমরা হিট করতে চাই।

  • Client (ব্রাউজার) → DNS দিয়ে হোস্টের IP খোঁজে (localhost-এর ক্ষেত্রে এই ধাপ লাগে না)
  • IP address-এর সাথে port number যুক্ত হয়
  • Request সেই port-এ শোনা (listen) সার্ভারে পৌঁছায়
  • সার্ভার (Spring Boot অ্যাপ্লিকেশন) endpoint অনুযায়ী response ফেরত পাঠায়

Spring Initializr দিয়ে প্রথম Spring Boot প্রজেক্ট তৈরি

Java দিয়ে scratch থেকে একটা web application বানাতে গেলে অনেক কিছু নিজে হাতে সেটআপ করতে হতো — proper folder structure বানানো, দরকারি configuration লেখা, আর প্রয়োজনীয় dependency (মানে অন্য কারো লেখা external library, যেমন কোনো DB connector) ডাউনলোড করা। এসবের একটাও কিন্তু আসল business logic নয়।

ঠিক এই সমস্যার সমাধানের জন্যই আছে Spring Initializr (start.spring.io) — এটা একটা ওয়েবসাইট, যেখানে কিছু অপশন সিলেক্ট করলেই একটা রেডি-মেড প্রজেক্ট skeleton (zip ফাইল আকারে) তৈরি করে দেয়। ফোল্ডার স্ট্রাকচার, Java version, Spring Boot version — সব আগে থেকেই কনফিগার করা থাকে, শুধু business logic লেখাটাই বাকি থাকে।

Spring Initializr-এ যেসব অপশন সিলেক্ট করা হয়েছে:

  • Project: Maven (Gradle-Groovy বা Gradle-Kotlin এর বদলে) — এটা একটা project management tool, বিস্তারিত পরের লেকচারে
  • Language: Java
  • Spring Boot version: 4.0.6 — সবচেয়ে স্টেবল ও লেটেস্ট ভার্সন বেছে নেওয়া হয়েছে (SNAPSHOT মানে এখনো "work in progress", RC মানে "release candidate" — এই দুটোই এড়িয়ে যাওয়া ভালো)
  • Packaging: Jar (Java Archive) — পুরনো WAR (Web Archive)-এর বদলে, আজকাল Spring Boot অ্যাপ্লিকেশন সাধারণত Jar-ই ব্যবহার করে
  • Configuration: Properties (YAML-এর বদলে)
  • Java version: 21
  • Dependency: Spring Web — এটা যোগ করলে অ্যাপ্লিকেশন RESTful web request handle করতে পারবে এবং by default embedded Apache Tomcat সার্ভার হিসেবে চলে আসবে (আলাদা করে Tomcat ইনস্টল করতে হবে না)

Generate করার পর zip ফাইলটা (এখানে নাম দেওয়া হয়েছে demo) unzip করে IDE-তে (IntelliJ IDEA) ওপেন করলে src/main/java/com/example/demo-এর ভেতর একটা মেইন ক্লাস পাওয়া যায়:

DemoApplication.java
package com.example.demo;

import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;

@SpringBootApplication
public class DemoApplication {

    public static void main(String[] args) {
        SpringApplication.run(DemoApplication.class, args);
    }

}

public static void main চেনা লাগছে — এটাই Java-র সাধারণ entry point। কিন্তু @SpringBootApplication অ্যানোটেশন আর SpringApplication.run(...) মেথড এখনো বোঝার দরকার নেই। শুধু এটা মনে রাখো — এই একটা লাইনই পুরো Spring Boot অ্যাপ্লিকেশনকে (embedded server-সহ) চালু করে দেয়।

খেয়াল রাখো: এই পর্যায়ে একটাও লাইন "business logic" লেখা হয়নি — শুধু কনফিগারেশন আর স্ট্রাকচার রেডি হয়েছে। Spring Boot-এর আসল সুবিধা হলো এই পুরো ধাপটা সে নিজে অটোমেটিক করে দেয়, যাতে ডেভেলপার সরাসরি নিজের লজিকে ফোকাস করতে পারে।

@RestController ও @GetMapping দিয়ে প্রথম Endpoint লেখা

শুরুতে সবচেয়ে সহজ পথ ছিল com.example.demo প্যাকেজে একটা নতুন Java class বানানো, নাম HelloController, আর তার ভেতর একটা সাধারণ মেথড লেখা যা একটা String রিটার্ন করে। এই মেথডকে main থেকে manual-ভাবে object বানিয়ে কল করেও console-এ print করানো যায় — কিন্তু সেটা তো পুরনো Java-র কায়দা, ব্রাউজার থেকে কল করার উপায় নয়।

ব্রাউজার থেকে /hello লিখলেই যেন এই মেথড অটোমেটিক কল হয়, তার জন্য দুটো অ্যানোটেশন লাগে —

  • @RestController — ক্লাসটাকে বলে দেয় এটা একটা "gateway", অর্থাৎ এখানে API endpoint লেখা হবে
  • @GetMapping("hello") — বলে দেয় কোন URL path (GET request) হিট হলে ঠিক এই মেথডটা কল হবে

এভাবে তৈরি হওয়া চূড়ান্ত কোড:

HelloController.java
package com.example.demo;

import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RestController;

@RestController
public class HelloController {

    // "/hello" endpoint হিট হলে এই মেথড কল হবে
    @GetMapping("hello")
    public String hello() {
        return "<h1>Hello World</h1>";
    }

    // মেথডের নাম আর endpoint-এর নাম এক হওয়া বাধ্যতামূলক নয়
    @GetMapping("bye")
    public String greetBye() {
        return "<h1>Bye</h1>";
    }
}

লক্ষ করার বিষয়, মেথডের নাম (hello, greetBye) আর endpoint path (hello, bye) এক হতে হবে এমন কোনো নিয়ম নেই — @GetMapping-এর ভেতরে যে string লেখা থাকে সেটাই আসল path ঠিক করে। এখানে return value-তে সরাসরি <h1> ট্যাগ ব্যবহার করা হয়েছে, ফলে ব্রাউজার সেটাকে HTML হিসেবে render করবে (শুধু plain text না)।

খেয়াল রাখো: এই পর্যায়ে @RestController বা @GetMapping ঠিক কীভাবে ভেতরে কাজ করে (mapping কীভাবে হয়, Tomcat কীভাবে শুরু হয়) — সেই internals এখনো ইচ্ছাকৃতভাবে শেখানো হয়নি। এই লেকচারের উদ্দেশ্য শুধু দেখানো যে Spring Boot দিয়ে কত দ্রুত একটা working endpoint বানানো যায়।

অ্যাপ্লিকেশন Run করা, Response দেখা ও পরের ধাপের ইঙ্গিত

DemoApplication ক্লাস run করলেই console-এ কিছু লগ দেখা যায়, যার মধ্যে গুরুত্বপূর্ণ লাইন — "Tomcat started on port 8080"। এর মানে, আমরা নিজে থেকে কোনো সার্ভার ইনস্টল করিনি; Spring Web dependency যোগ করার সাথে সাথেই embedded Tomcat সার্ভার অটোমেটিক চালু হয়ে গেছে।

localhost:8080/hello-এ গিয়ে endpoint তৈরির আগে হিট করলে একটা Whitelabel Error Page দেখা যায় ("no explicit mapping for /error") — এর মানে সার্ভার চলছে ঠিকই, কিন্তু ওই path-এর জন্য কোনো mapping (আমাদের controller মেথড) নেই। HelloController তৈরি ও অ্যানোটেশন যোগ করার পর অ্যাপ্লিকেশন আবার run (rerun) করলে ব্রাউজারে ঠিক ঠিক "Hello World" (এখানে <h1> ট্যাগ-সহ বড় হরফে) দেখা যায়।

Server-এর port পরিবর্তন করাও সহজ — src/main/resources/application.properties ফাইলে server.port সেট করলেই Tomcat সেই নতুন port-এ চালু হবে:

application.properties
spring.application.name=demo
server.port=9090

এই পরিবর্তনের পর পুরনো localhost:8080 আর কাজ করবে না ("this site can't be reached") — এখন হিট করতে হবে localhost:9090/hello। এখান থেকে বোঝা যায়, port শোনার (listen) কাজটা Spring Boot অ্যাপ্লিকেশন নয়, বরং তার ভেতরের embedded Tomcat সার্ভার করে।

প্রায় ১০ মিনিটে একটা সম্পূর্ণ কাজ করা Spring Boot অ্যাপ্লিকেশন তৈরি হয়ে গেল — কোনোরকম manual configuration ছাড়াই। এখানেই দেখানো হলো Spring Boot কতটা দ্রুত auto-configuration করে দেয়, যাতে ডেভেলপার সরাসরি business logic-এ মন দিতে পারে।

পরের লেকচারের ইঙ্গিত: Spring Initializr-এ যে "Maven" বেছে নেওয়া হয়েছিল, সেটা আসলে একটা project management tool — Java প্রজেক্টের dependency এবং build পরিচালনা করে। Maven ঠিক কীভাবে কাজ করে, তার গভীর আলোচনা পরের লেকচারে হবে; এই লেকচারে শুধু এটুকু জানলেই যথেষ্ট যে Maven আমাদের প্রজেক্ট ম্যানেজ করছে। একইভাবে @RestController, @GetMapping, বা Tomcat কীভাবে ভেতরে ভেতরে কাজ করে (Spring Core-এর internals) — সেটাও পরের ক্লাসগুলোতে ধাপে ধাপে খোলা হবে।
অনুশীলন প্রশ্ন
  1. HelloController-এ নতুন একটা /greet endpoint বানাও যেটা @GetMapping ব্যবহার করে একটা কাস্টম স্ট্রিং (যেমন "Welcome!") রিটার্ন করে।
  2. application.properties-এ server.port পরিবর্তন করে দেখো — পরিবর্তনের পর কেন পুরনো port-এ "this site can't be reached" দেখায়, তা নিজের ভাষায় ব্যাখ্যা করো।
  3. @RestController আর @GetMapping ছাড়া শুধু main মেথড থেকে manual-ভাবে controller-এর মেথড কল করলে কেন সেটা ব্রাউজার থেকে অ্যাক্সেস করা যায় না — এই পার্থক্যটা লিখে ব্যাখ্যা করো।

JAR ফাইল ও Maven কেন দরকার

Maven বোঝার আগে বুঝতে হবে JAR (Java Archive) ফাইল আসলে কী। ধরো তুমি জাভায় একটা প্রোজেক্ট লিখছো — Order.java, User.java, Payment.java এরকম অনেক ক্লাস আছে। এগুলো এক এক করে কম্পাইল করলে অনেক .class ফাইল তৈরি হবে। এখন এই পুরো প্রোজেক্টটা যদি বন্ধুর সাথে শেয়ার করতে হয়, প্রতিটা ফাইল আলাদা করে পাঠানো খুবই বাজে পদ্ধতি — ফোল্ডার স্ট্রাকচার নষ্ট হতে পারে, কিছু রিসোর্স ফাইল মিস হয়ে যেতে পারে।

এই সমস্যার সমাধান হিসেবে এসেছে JAR — এটা অনেকটা একটা ZIP ফাইলের মতো, যার ভেতরে একাধিক .class ফাইল, রিসোর্স (image, properties file) এবং প্যাকেজ/ফোল্ডার একসাথে প্যাক করা থাকে। JAR-কে তাই একটা প্যাকেজ বলা যায়, যেটা কারো সাথে শেয়ার করা অনেক সহজ।

JAR এর দুইটা বড় সুবিধা আছে। প্রথমত, নিজের কোড/লাইব্রেরি সহজে শেয়ার করা যায়। দ্বিতীয়ত, অন্যের বানানো third-party library-ও একই ভাবে JAR হিসেবে নিজের প্রোজেক্টে ব্যবহার করা যায় — যেমন ডেটাবেসের সাথে কানেক্ট করতে হলে MySQL Connector-এর JAR লাগবে।

Library বনাম Application — Library হলো এমন কোড যেটা নিজে থেকে রান হয় না (কোনো main ফাংশন নেই), শুধু কিছু ক্লাস/মেথড থাকে যেগুলো অন্য কেউ ব্যবহার করে। Application হলো যেটা independently রান করা যায় — এর ভেতরে একটা main ফাংশন থাকে। যখন কোনো লাইব্রেরি কোনো অ্যাপ্লিকেশনের ভেতরে ব্যবহার হয়, তখন সেই লাইব্রেরিকে বলা হয় ওই অ্যাপ্লিকেশনের dependency।

খেয়াল রাখো: Library-র JAR বানালে তার ভেতরে external dependency-র JAR গুলো থাকে না — শুধু নিজের কোড থাকে। কিন্তু কোনো Application (যেমন Spring Boot অ্যাপ)-এর JAR বানালে সেটা হয়ে যায় executable JAR — সব dependency সহ, যেটা independently রান করা যায়। Library-র JAR হলো non-executable JAR — এর dependency-র তথ্য থাকে একটা স্পেশাল ফাইলে, যার নাম pom.xml (Maven ব্যবহার করলে)।

রান-টাইমে যখন নিজের কোড এবং third-party লাইব্রেরির কোড একসাথে দরকার হয়, তখন JVM একটা বিশেষ জায়গায় ক্লাস খুঁজে বের করে — একে বলে classpath। প্রথমে নিজের কোডে খোঁজে, না পেলে dependency-র JAR গুলোর bytecode-এ খোঁজে।

এখন আসল সমস্যা — এই dependency-গুলো কীভাবে জোগাড় করবে? একটা উপায় হলো ম্যানুয়ালি গিয়ে গুগল করে JAR ডাউনলোড করা (যেমন mysql.com থেকে সরাসরি)। এটা একটা-দুইটা dependency-র জন্য ঠিক আছে, কিন্তু বাস্তব প্রোজেক্টে শত শত dependency লাগে, যার প্রতিটার version মেলাতে হয়, আর একটা dependency আবার আরেকটার উপর নির্ভর করে (একে বলে transitive dependency)। এই পুরো ম্যানুয়াল ঝামেলা, version mismatch-এর ঝুঁকি, আর transitive dependency ট্র্যাক করার কষ্ট — এসবের সমাধান হিসেবেই আসে Maven।

Maven আসলে কী — একটি Project Management Tool

সংক্ষেপে বলতে গেলে, Maven হলো একটা project management tool — যেটা তোমার প্রোজেক্ট ম্যানেজ করার সব ঝামেলা নিজে হ্যান্ডেল করে নেয়, যাতে তুমি শুধু নিজের business logic নিয়ে ফোকাস করতে পারো। বাজারে Maven ছাড়াও Gradle আছে, কিন্তু Maven সবচেয়ে বেশি ব্যবহৃত হয় এবং শেখাও তুলনামূলক সহজ।

মূলত Maven চারটা কাজ করে —

  • একটা নির্দিষ্ট ফোল্ডার স্ট্রাকচার মেইনটেইন করে — টিমের সবাই যেন একই স্ট্যান্ডার্ড স্ট্রাকচার ফলো করে, কেউ নিজের মতো আলাদা প্লেসে ফাইল না রাখে
  • জাভা কোড কম্পাইল করে দেয় — এক ক্লিকে পুরো প্রোজেক্টের সব ক্লাস কম্পাইল হয়ে যায়
  • কোডের JAR ফাইল বানিয়ে দেয় (packaging)
  • প্রয়োজনীয় সব dependency ডাউনলোড করে দেয় ইন্টারনেট থেকে — transitive dependency সহ, ম্যানুয়ালি কিছুই করতে হয় না
Build Systemমন্তব্য
IntelliJ-এর নিজস্ব বিল্ড সিস্টেমশুধু IntelliJ ব্যবহারকারীদের জন্যই কাজ করবে, টিমে সবাই ভিন্ন IDE ব্যবহার করলে ফোল্ডার স্ট্রাকচার আলাদা হয়ে যাবে
Mavenযে কোনো IDE (IntelliJ, Eclipse, NetBeans) থেকে একই স্ট্যান্ডার্ড ফলো করা যায়; ওয়াইডলি ইউজড
GradleMaven-এর বিকল্প, একই কাজ করে কিন্তু ভিন্ন সিনট্যাক্স ও ফাইলে (Groovy/Kotlin DSL)

Build system বলতে বোঝায় — তোমার কোড কীভাবে বিল্ড হবে, কীভাবে কম্পাইল হবে, কীভাবে প্যাকেজ হবে, dependency কীভাবে ডাউনলোড হবে — সেই পুরো নিয়মকানুন। টিমে সবাই একই build system ব্যবহার করলে কনসিসটেন্সি বজায় থাকে।

Maven প্রজেক্ট ও ফোল্ডার স্ট্রাকচার (IntelliJ)

IntelliJ-তে Maven প্রি-ইনস্টলড থাকে, তাই আলাদা করে ইনস্টল করার দরকার নেই। New Project করার সময় build system হিসেবে Maven বেছে নিলে, groupId ও artifactId জিজ্ঞেস করা হয় — এই লেকচারের ডেমো প্রোজেক্টের নাম MavenDemo, groupId org.example।

প্রোজেক্ট তৈরি হলে দুইটা মূল জিনিস গুরুত্বপূর্ণ — src ফোল্ডার এবং pom.xml ফাইল। বাকি (.idea, .gitignore, .mvn) IDE/Maven-এর internal ফাইল, ইগনোর করা যায়।

src-এর ভেতরে দুইটা ফোল্ডার — main ও test। আসল বিজনেস লজিক থাকে main-এ, আর ইউনিট টেস্ট কেস (JUnit, Mockito দিয়ে লেখা) থাকে test-এ। main-এর ভেতরে আবার দুইটা ফোল্ডার — java (সব .java ফাইল) এবং resources (non-java ফাইল, যেমন properties, static image)।

ফোল্ডার স্ট্রাকচার (groupId = org.example)
MavenDemo/
├── pom.xml
└── src/
    ├── main/
    │   ├── java/
    │   │   └── org/example/
    │   │       ├── Main.java
    │   │       ├── Demo.java
    │   │       ├── Demo2.java
    │   │       └── controller/
    │   │           └── HelloController.java
    │   └── resources/
    └── test/
        └── java/

লক্ষ্য করো — groupId ছিল org.example, আর Maven সেই অনুযায়ী java ফোল্ডারের ভেতরে org-এর ভেতরে example নামে ফোল্ডার বানিয়ে দিয়েছে (ডট মানেই নেস্টেড ফোল্ডার)। নিজের সব জাভা ফাইল এই org/example-এর ভেতরেই লিখতে হয়, যেমন এখানে controller নামে সাব-প্যাকেজ বানিয়ে HelloController রাখা হয়েছে।

খেয়াল রাখো: যখন কম্পাইল/রান করা হয়, Maven একটা target ফোল্ডার বানায় যেখানে classes সাব-ফোল্ডারে ঠিক একই ফোল্ডার হায়ারার্কি (org/example/...) বজায় রেখে .class (bytecode) ফাইলগুলো রাখা হয়। target ফোল্ডার ডিলিট করে দিলেও চিন্তা নেই — আবার compile/run করলেই সেটা রিজেনারেট হয়ে যায়।

IntelliJ-এর ডান পাশে একটা Maven প্যানেল থাকে যেখানে Lifecycle, Plugins, ও Dependencies ট্যাব দেখা যায় — এখান থেকে ক্লিক করেই compile, package ইত্যাদি ফেজ রান করা যায়।

pom.xml — প্রজেক্টের পরিচয়পত্র

pom.xml হলো Maven-এর সবচেয়ে গুরুত্বপূর্ণ ফাইল। এর ফুল ফর্ম Project Object Model XML। এটাতে প্রোজেক্ট সম্পর্কে সব তথ্য থাকে — নাম, ভার্সন, কী কী third-party লাইব্রেরি লাগবে, কী কী plugin লাগবে ইত্যাদি।

pom.xml (আসল প্রোজেক্ট থেকে)
<?xml version="1.0" encoding="UTF-8"?>
<project xmlns="http://maven.apache.org/POM/4.0.0"
         xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
         xsi:schemaLocation="http://maven.apache.org/POM/4.0.0 http://maven.apache.org/xsd/maven-4.0.0.xsd">

    <modelVersion>4.0.0</modelVersion>

    <groupId>org.example</groupId>
    <artifactId>MavenDemo</artifactId>
    <version>1.0-SNAPSHOT</version>

    <packaging>jar</packaging>

    <dependencies>
        <dependency>
            <groupId>com.mysql</groupId>
            <artifactId>mysql-connector-j</artifactId>
            <version>9.5.0</version>
            <scope>compile</scope>
        </dependency>

        <dependency>
            <groupId>org.hibernate.orm</groupId>
            <artifactId>hibernate-core</artifactId>
            <version>7.3.6.Final</version>
            <scope>compile</scope>
        </dependency>
    </dependencies>

    <properties>
        <maven.compiler.source>23</maven.compiler.source>
        <maven.compiler.target>23</maven.compiler.target>
        <project.build.sourceEncoding>UTF-8</project.build.sourceEncoding>
    </properties>

</project>

প্রতিটা pom.xml শুরু হয় রুট ট্যাগ <project> দিয়ে। এর পরের xmlns/xsi:schemaLocation লাইনগুলো হলো schema — এটা বলে দেয় কোন ট্যাগ ব্যবহার করা বৈধ (allowed), কোনটা না। মনগড়া কোনো ট্যাগ বসালে IntelliJ সাথে সাথে "invalid context" এরর দেখাবে।

<modelVersion> মানে pom-এর নিজের মডেলের ভার্সন (৪.০.০), এটা Maven সফটওয়্যারের ভার্সন থেকে আলাদা জিনিস।

সবচেয়ে গুরুত্বপূর্ণ তিনটা ট্যাগ — GAV (groupId, artifactId, version)। এই তিনটা মিলে সারা পৃথিবীতে প্রোজেক্টকে ইউনিকলি আইডেন্টিফাই করে।

  • groupId — সাধারণত নিজের ডোমেইন নাম উল্টো করে লেখা হয় (কনভেনশন), যেমন coderarmy.in থাকলে in.coderarmy। নিজের ডোমেইন না থাকলে org.example-এর মতো কিছু ব্যবহার করা যায়
  • artifactId — প্রোজেক্টের নাম, এখানে MavenDemo
  • version — যেমন 1.0-SNAPSHOT। "SNAPSHOT" মানে প্রোজেক্ট এখনো কাজ চলছে (working phase); কাজ শেষ হলে SNAPSHOT সরিয়ে একটা স্থায়ী ভার্সন নাম্বার দেওয়া হয়

<properties> ট্যাগে key-value পেয়ার রাখা যায় — যেমন maven.compiler.source। চাইলে নিজের কাস্টম key-ও বানানো যায় (যেমন author.name), এবং পুরো ফাইলে যেকোনো জায়গায় সেটা ${key.name} সিনট্যাক্স দিয়ে রেফার করা যায়।

<packaging> ট্যাগে jar বা war (Web Archive) লেখা যায়; কিছু না লিখলে ডিফল্ট jar-ই হয়।

খেয়াল রাখো: pom.xml-এও ইনহেরিটেন্স আছে। প্রতিটা pom-এর একটা parent থাকে — কিছু উল্লেখ না করলে ডিফল্ট parent হয় Super POM (ঠিক যেমন জাভায় কোনো ক্লাস কিছু extend না করলে বাই ডিফল্ট Object ক্লাস inherit করে)। IntelliJ-তে Show Effective POM-এ ক্লিক করলে দেখা যায় নিজের pom + সব parent pom মিলিয়ে চূড়ান্ত যে pom Maven আসলে ব্যবহার করে, সেটাকে বলে Effective POM। Spring Boot প্রোজেক্টে parent হিসেবে spring-boot-starter-parent থাকে, যেটার আবার নিজস্ব parent chain আছে, শেষে গিয়ে Super POM-এ পৌঁছায়।

Dependency যোগ করা — Maven Repository ওয়েবসাইট ও Transitive Dependency

কোনো dependency-র exact groupId/artifactId/version মুখস্থ রাখার দরকার নেই। এর জন্য আছে mvnrepository.com নামের একটা ওয়েবসাইট — এখানে dependency-র নাম সার্চ করলে তার সব ভার্সনের Maven স্নিপেট পাওয়া যায়, সোজা কপি-পেস্ট করে <dependencies> ট্যাগের ভেতরে বসিয়ে দিলেই হয়।

খেয়াল রাখো: সবসময় একদম সর্বশেষ (latest) ভার্সন নেওয়া ভালো প্র্যাকটিস নয় — এতে বাগ থাকার সম্ভাবনা বেশি, কম মানুষ ব্যবহার করে থাকে। আবার খুব পুরনো ভার্সনও নেওয়া ঠিক না। মাঝামাঝি একটা স্টেবল, বহুল-ব্যবহৃত ভার্সন বেছে নেওয়াই ভালো (যেমন mysql-connector-j-এর জন্য 9.5.0)।

শুধু pom.xml-এ dependency লিখলেই সেটা অটোমেটিক ডাউনলোড হয়ে যায় না — IntelliJ-তে একটা reload/sync আইকনে ক্লিক করতে হয় (বা Maven প্যানেল থেকে reload), তখনই Maven সেই dependency ইন্টারনেট থেকে ডাউনলোড করে এবং External Libraries-এর ভেতরে দেখা যায়।

এখানে একটা ইন্টারেস্টিং জিনিস দেখা যায় — শুধু একটা mysql-connector-j লিখলেও এর সাথে আরেকটা dependency (যেমন Google Protobuf) নিজে থেকেই চলে আসে। এটাকে বলে transitive dependency — অর্থাৎ যে dependency চাওয়া হয়েছে, সেটা চলতে গেলে নিজেই আরও কিছু dependency-র উপর নির্ভর করে, আর Maven সেগুলোও নিজে থেকেই ডাউনলোড করে দেয়।

একইভাবে hibernate-core যোগ করলে দেখা যায় সেটা নিজে অনেকগুলো dependency-র উপর নির্ভর করে (Jakarta, Glassfish, Eclipse ইত্যাদির প্যাকেজ), আর সেগুলোর প্রতিটাও আবার আরও গভীরে নিজস্ব transitive dependency টেনে আনে। Maven প্যানেলের Dependencies ট্যাবে এই পুরো হায়ারার্কি (tree) দেখা যায়।

ট্যাগমানে
groupId (dependency-র)যে লাইব্রেরি ডাউনলোড করছি তার প্রকাশকের গ্রুপ আইডি, যেমন com.mysql
artifactId (dependency-র)ওই লাইব্রেরির প্রোজেক্ট নাম, যেমন mysql-connector-j
versionকোন ভার্সন লাগবে
scope (ঐচ্ছিক)কোন ফেজে এই dependency লাগবে তা বলে দেয়; ডিফল্ট মান compile

ম্যানুয়ালি করলে যে কাজে অনেক সময় ও effort লাগতো, সেই একই কাজ এখানে শুধু dependency-র নাম বসিয়ে দিয়ে সেকেন্ডের মধ্যে হয়ে যায় — এটাই Maven-এর সবচেয়ে বড় সুবিধা।

Local vs Remote Repository — Maven Central ও .m2 ফোল্ডার

Maven মূলত দুই ধরনের repository ব্যবহার করে — Maven Central (remote) এবং Local Repository। এছাড়াও কোম্পানি-নির্দিষ্ট প্রাইভেট রিমোট repository-ও থাকতে পারে।

Repositoryবিবরণ
Maven Centralএকটা বিশাল রিমোট রিপোজিটরি যেখানে হাজার হাজার JAR ফাইল রাখা আছে; Maven ডিফল্টভাবে এখান থেকেই dependency ডাউনলোড করে (Effective POM-এ এর URL declare করা থাকে)
Local Repository (.m2)নিজের কম্পিউটারে একটা হিডেন ফোল্ডার (.m2/repository) — এখানে আগে ডাউনলোড করা সব dependency এবং নিজের বানানো JAR ক্যাশ হয়ে থাকে
Other Remote Repositoryকোম্পানির নিজস্ব প্রাইভেট রিমোট রিপোজিটরি — প্রাইভেট ইন্টারনাল লাইব্রেরি রাখতে, বা সিকিউরিটির জন্য শুধু ট্রায়েড-অ্যান্ড-টেস্টেড আর্টিফ্যাক্ট ব্যবহার করতে

Dependency ডাউনলোডের পুরো ফ্লো এরকম —

  • Maven প্রথমে pom.xml পড়ে দেখে কোন dependency লাগবে
  • প্রথমে চেক করে local repository-তে (.m2/repository) এটা আগে থেকে আছে কিনা
  • লোকালি পেলে সেখান থেকেই ব্যবহার করে নেয় — কোনো ইন্টারনেট লাগে না, তাই দ্রুত হয়
  • লোকালি না পেলে Maven Central (বা override করা থাকলে কোম্পানির নিজস্ব রিমোট রিপোজিটরি) থেকে ডাউনলোড করে
  • ডাউনলোড করার পরে সেটা .m2-তেও কপি রেখে দেয় (cache করে), যাতে পরের বার আর ইন্টারনেট থেকে আনতে না হয়
খেয়াল রাখো: এই জন্যই প্রথমবার প্রোজেক্ট বিল্ড করলে একটু সময় লাগে (সব dependency ইন্টারনেট থেকে আসে), কিন্তু পরের বার থেকে অনেক দ্রুত হয়ে যায় (local cache থেকে আসে)। ডিফল্টে <repository> ট্যাগ override করে নিজের কোম্পানির রিমোট repository-র URL ব্যবহার করা সম্ভব <repositories> ট্যাগ দিয়ে।

নিজের বানানো JAR-এর নামকরণও এই একই GAV কনভেনশন মেনে হয় — artifactId-version.jar। যেমন এই ডেমো প্রোজেক্টের artifactId MavenDemo আর version 1.0-SNAPSHOT হওয়ায় জেনারেট হওয়া JAR-এর নাম হয় MavenDemo-1.0-SNAPSHOT.jar। এই একই নিয়মে .m2-এর ভেতরে ফোল্ডার স্ট্রাকচারও তৈরি হয় — groupId/artifactId/version/artifactId-version.jar।

.m2 local repository — ফোল্ডার স্ট্রাকচার
~/.m2/repository/
└── org/example/MavenDemo/1.0-SNAPSHOT/
    └── MavenDemo-1.0-SNAPSHOT.jar

~/.m2/repository/
└── com/mysql/mysql-connector-j/9.5.0/
    └── mysql-connector-j-9.5.0.jar

Maven Build Lifecycle — Validate থেকে Deploy পর্যন্ত

যখন জাভা কোড লিখে সেটাকে রান করা হয়, তখন এর মাঝখানে অনেকগুলো অদৃশ্য ফেজ (phase) থাকে। Maven এই সব ফেজকে সুসংগঠিতভাবে হ্যান্ডেল করে — একে বলে Build Lifecycle। Maven-এর পুরো lifecycle মূলত তিন ভাগে ভাগ করা —

Lifecycleফেজ
Clean Lifecycleশুধু clean — একটা মাত্র ফেজ, এটা স্বাধীন
Default Lifecyclevalidate → compile → test → package → verify → install → deploy
Site Lifecycleশুধু site — ডকুমেন্টেশন/রিপোর্ট বানানোর জন্য

Default Lifecycle-ই সবচেয়ে গুরুত্বপূর্ণ, কারণ এখানে একাধিক ফেজ আছে যেগুলো নির্দিষ্ট ক্রম মেনে একের পর এক ঘটে —

  • validate — প্রোজেক্টের স্ট্রাকচার ঠিক আছে কিনা চেক করে; pom.xml আছে কিনা, সেটা readable কিনা, দরকারি সব ডিটেইল ঠিকঠাক আছে কিনা
  • compile — .java ফাইলগুলোকে .class-এ কনভার্ট করে, target/classes-এর ভেতরে রাখে
  • test — নিজের লেখা ইউনিট টেস্ট কেসগুলো (JUnit/Mockito দিয়ে) রান করে
  • package — কম্পাইল হওয়া কোড থেকে JAR (বা WAR) ফাইল বানায়, target-এর ভেতরে রাখে
  • verify — integration testing বা code quality চেক করার জায়গা; এখানে অতিরিক্ত plugin (pom.xml-এর <plugins> ট্যাগে) যোগ করে বাড়তি চেক করা যায়
  • install — বানানো JAR-কে নিজের local repository (.m2)-তে ইনস্টল করে দেয়, যাতে অন্য লোকাল প্রোজেক্ট থেকেও এটা dependency হিসেবে ব্যবহার করা যায়
  • deploy — install করা আর্টিফ্যাক্টকে কোম্পানির রিমোট রিপোজিটরিতে আপলোড করে দেয়, যাতে টিমের অন্য সবাই এটা ব্যবহার করতে পারে
খেয়াল রাখো: এই ফেজগুলো লিনিয়ার — কোনো একটা ফেজে ক্লিক করলে তার আগের সব ফেজ automatically ঘটে যায়। যেমন package-এ ক্লিক করলে আগে validate, তারপর compile, তারপর test — এই সব হয়ে তবেই JAR বানানো হয়। আর deploy মানে কিন্তু Git-এ push করা না — এটা শুধু নিজের কোম্পানির private remote repository-তে JAR/artifact আপলোড করা, যাতে টিমের বাকিরা সেটা dependency হিসেবে ব্যবহার করতে পারে।

এই ফেজগুলো IntelliJ-এর Maven প্যানেল থেকে ক্লিক করেও চালানো যায়, আবার টার্মিনাল থেকে কমান্ড দিয়েও — যেমন mvn compile, mvn install। দুইটা ভিন্ন lifecycle-এর ফেজ একসাথেও চালানো যায়, যেমন সবচেয়ে জনপ্রিয় কমান্ড mvn clean install — এটা প্রথমে পুরোনো target ফোল্ডার মুছে (clean lifecycle থেকে), তারপর validate → compile → test → package → verify → install (default lifecycle থেকে) — পুরো চেইন চালিয়ে local repository-তে ফ্রেশ JAR বসিয়ে দেয়।

টাইট কাপলিং সমস্যা — OrderService নিজেই EmailService বানাচ্ছে

Spring শেখার আগে এই লেকচারে ইচ্ছে করেই Spring ছাড়া প্লেইন Java-তে একটা ছোট্ট কনসোল প্রজেক্ট (CoreDemo) বানানো হয়েছে, শুধু এটা বোঝানোর জন্য যে Dependency Injection আর Inversion of Control (IoC) আসলে কোন সমস্যার সমাধান — এগুলো Spring-এর নিজস্ব আবিষ্কার নয়, এগুলো ভালো Java ডিজাইনের নিয়ম, যেটার উপর Spring-এর পুরো আইডিওলজি দাঁড়িয়ে আছে।

শুরুতে সবচেয়ে সহজ, সরল একটা ডিজাইন দিয়ে শুরু হয়েছে। একটা OrderService ক্লাস আছে যার কাজ অর্ডার প্লেস করা, আর অর্ডার প্লেস হলে ইউজারকে একটা নোটিফিকেশনও পাঠাতে হবে — তার জন্য একটা EmailService ক্লাস। সবচেয়ে সোজা উপায় হলো OrderService-এর ভেতরেই সরাসরি new EmailService() লিখে অবজেক্ট বানিয়ে ফেলা।

শুরুর ডিজাইন (এখনো interface ছাড়া)
public class OrderService {

    // EmailService-এর অবজেক্ট নিজেই বানিয়ে নিচ্ছে
    EmailService emailService = new EmailService();

    public void placeOrder() {
        System.out.println("Order placed");
        // actual business logic..
        emailService.sendNotification();
    }
}

এখানে OrderService একটা EmailService-এর উপর ডিপেন্ডেন্ট — যতক্ষণ না EmailService-এর অবজেক্ট বানানো হয়েছে, ততক্ষণ placeOrder() মেথডটাই কাজ করবে না। এটাকেই বলে dependency। কোডে dependency থাকা কোনো সমস্যা না — বাস্তব প্রজেক্টে শত শত ক্লাস একে অপরের উপর নির্ভর করেই থাকবে। আসল সমস্যাটা অন্য জায়গায়।

এখানে দুটো জিনিস একসাথে ঘটছে যেটা টাইট কাপলিং (tight coupling) তৈরি করে —

  • OrderService সরাসরি একটা concrete class (EmailService)-এর সাথে বাঁধা পড়ে গেছে, কোনো abstraction / interface ছাড়াই — কাল যদি SMS বা Pop-up নোটিফিকেশন পাঠাতে হয়, তাহলে OrderService-এর ভেতরে ঢুকে কোড পাল্টাতে হবে, যেটা Open-Closed Principle ভাঙে (ক্লাস extend করা যাবে, কিন্তু modify করা উচিত না)।
  • OrderService নিজের dependency নিজেই তৈরি করছে — অর্থাৎ সে অর্ডার ম্যানেজ করার পাশাপাশি নোটিফিকেশন অবজেক্ট বানানোর কাজটাও করছে। এতে Single Responsibility Principle ভাঙে, কারণ একটা ক্লাসের একাধিক কাজ (multiple responsibility) থেকে যাচ্ছে।
খেয়াল রাখো: অবজেক্ট বানানো নিজে কোনো সমস্যা না। সমস্যা হলো — কোথায় বানানো হচ্ছে। OrderService-এর কাজ হওয়া উচিত অর্ডার ম্যানেজ করা, অন্য কোনো ক্লাসের অবজেক্ট বানানো (factory-র কাজ) না।

ইন্টারফেস দিয়ে ধাপ ১ — NotificationService abstraction, তবু আসল সমস্যা রয়েই গেল

Java-তে সাধারণ নিয়ম হলো, যতটা সম্ভব interface-এর সাথে কোড করা উচিত, concrete class-এর সাথে নয়। তাই প্রথম ধাপ হলো একটা কমন NotificationService interface বানানো — কারণ Email, SMS বা Pop-up, এরা সবাই আসলে এক ধরনের নোটিফিকেশনই পাঠায়।

NotificationService.java
package in.coderarmy.notification;

public interface NotificationService {
    void sendNotification();
}

এরপর EmailService-কে এই interface implements করানো হয়, আর কোড পরিষ্কার রাখতে সব নোটিফিকেশন-রিলেটেড ক্লাসকে আলাদা notification প্যাকেজে সরিয়ে নেওয়া হয়। OrderService-এর ভেতরেও ভ্যারিয়েবলের টাইপ এখন concrete class না হয়ে interface হয়ে যায়।

মাঝামাঝি ধাপ — টাইপ interface, কিন্তু object তৈরি এখনও ভেতরেই
public class OrderService {

    NotificationService notification = new EmailService();

    public void placeOrder() {
        System.out.println("Order placed");
        notification.sendNotification();
    }
}

এখন notification ভ্যারিয়েবলের রেফারেন্স টাইপ NotificationService (interface), EmailService নয় — এই পর্যন্ত ভালো লাগছে। EmailService-এর বদলে SmsService লিখলেও কোড ঠিকভাবে কম্পাইল ও রান হয়ে যায়, কারণ parent interface-এর reference variable child class-এর object কল করতে পারে (Java-এর বেসিক পলিমরফিজম নিয়ম)।

খেয়াল রাখো: এখানে একটা ফাঁদ আছে — ভ্যারিয়েবলের টাইপ interface হয়ে গেলেও, আসল object টা এখনো OrderService-এর ভেতরেই new EmailService() দিয়ে concrete-ভাবে তৈরি হচ্ছে। তাই টাইট কাপলিং আসলে এখনো দূর হয়নি — শুধু ভ্যারিয়েবলের ডিক্লেয়ারেশন বদলেছে, দায়িত্ব বদলায়নি। নতুন নোটিফিকেশন টাইপে সুইচ করতে গেলে এখনো OrderService-এর ভেতরেই ঢুকে কোড এডিট করতে হচ্ছে।

Main-এ ম্যানুয়াল Dependency Injection — Constructor ও Setter Injection

এখন আসল সমাধান — OrderService নিজে থেকে কোনো NotificationService তৈরি করবে না, বরং বাইরে থেকে কেউ তাকে সেই dependency-টা পাঠিয়ে দেবে (inject করবে)। এর জন্য একটা constructor বানানো হয়, যেখানে OrderService শুধু বলে দেয় তার কী চাই — একটা NotificationService — কীভাবে সেটা বানানো হবে সেটা তার মাথাব্যথা নয়।

OrderService.java (আসল কোড)
package in.coderarmy;

import in.coderarmy.notification.EmailService;
import in.coderarmy.notification.NotificationService;
import in.coderarmy.notification.PopUpNotificationService;
import in.coderarmy.notification.SmsService;

public class OrderService {

    NotificationService notification;

    public OrderService(NotificationService notification) {
        this.notification = notification;
    }

    public OrderService() {

    }

    public void placeOrder() {
        System.out.println("Order placed");
        // actual business logic..
        notification.sendNotification();
    }

    public void setNotification(NotificationService notification) {
        this.notification = notification;
    }
}

লক্ষ্য করো, OrderService-এ dependency ইনজেক্ট করার দুই রকম রাস্তা রাখা হয়েছে —

  • Constructor Injection — প্যারামিটার-ওয়ালা কনস্ট্রাক্টর দিয়ে, অবজেক্ট তৈরির সময়েই dependency পাস করে দেওয়া।
  • Setter Injection — একটা খালি (no-arg) কনস্ট্রাক্টর দিয়ে আগে অবজেক্ট বানিয়ে, পরে setNotification() মেথড কল করে dependency বসিয়ে দেওয়া।

এই পুরো কাজটা — কে কার dependency, কীভাবে সেগুলো একসাথে জোড়া লাগবে (wiring) — এখন Main ক্লাসের দায়িত্ব হয়ে গেছে।

Main.java (আসল কোড)
package in.coderarmy;

import in.coderarmy.notification.*;

public class Main {
    public static void main(String[] args) {
        NotificationService notification = new EmailService();
        //OrderService order = new OrderService(notification);
        OrderService order = new OrderService();
        order.setNotification(notification);
        order.placeOrder();
    }
}

// build everything itself

// IOC --> Inversion of control

এখানে Main-ই প্রথমে EmailService-এর অবজেক্ট বানাচ্ছে, তারপর OrderService-এর অবজেক্ট বানাচ্ছে, আর শেষে setNotification() দিয়ে dependency-টা জোড়া লাগিয়ে দিচ্ছে (কমেন্ট করা লাইনটা দেখালে বোঝা যায়, চাইলে constructor injection দিয়েও একই কাজ সরাসরি এক লাইনে করা যেত)। নোটিফিকেশন টাইপ বদলাতে হলে এখন শুধু Main-এর একটা লাইন বদলালেই হয় (new EmailService() → new SmsService()) — OrderService-এর কোডে কোনো হাতই দিতে হয় না।

খেয়াল রাখো: এই কৌশলের বিখ্যাত এক লাইনের সারমর্ম — "Don't create your own dependency, get your dependency", অথবা "A class should ask what it needs and not build everything itself"। Dependency Injection-এর তিন নম্বর একটা ধরনও আছে — Field Injection — কিন্তু প্লেইন Java-তে সেটা সরাসরি সম্ভব না; সেটা Spring Framework ব্যবহার করলে তবেই বোঝা যাবে।

Inversion of Control (IoC) — কন্ট্রোলের ফ্লো উল্টে যাওয়া

Dependency Injection বোঝা হয়ে গেলে Inversion of Control (IoC) বোঝা কঠিন কিছু না — অনেকে এই দুটো টার্ম মিলিয়েও ফেলে, কিন্তু আসলে এরা আলাদা জিনিস, শুধু খুব কাছাকাছি সম্পর্কিত। IoC হলো একটা principle / আইডিয়া, আর Dependency Injection হলো সেই আইডিয়া বাস্তবায়ন করার একটা টেকনিক।

জিনিসটা বোঝার জন্য দেখা যাক, dependency injection-এর আগে আর পরে "কন্ট্রোল" কোন দিকে বইছিল —

Injection-এর আগে: Main ──creates──► OrderService ──creates──► EmailService (কন্ট্রোল OrderService-এর ভেতরে ছিল) Injection-এর পরে: Main ──creates──► EmailService Main ──creates──► OrderService Main ──provides (EmailService)──► OrderService (কন্ট্রোল এখন বাইরে, Main-এর হাতে)

Injection-এর আগে OrderService-ই সিদ্ধান্ত নিচ্ছিল কোন EmailService ব্যবহার হবে এবং কীভাবে সেটা তৈরি হবে — অর্থাৎ কন্ট্রোল ছিল OrderService-এর নিজের ভেতরে (inside)। Injection করার পর সেই সিদ্ধান্তটা OrderService-এর হাত থেকে বেরিয়ে গিয়ে Main-এর হাতে চলে গেছে — এখন OrderService শুধু যেটা পাচ্ছে সেটা ব্যবহার করে, নিজে কিছু ঠিক করে না। অর্থাৎ কন্ট্রোল আগে যেখানে ছিল (inside), সেখান থেকে সরে বাইরে (outside) চলে গেছে — কন্ট্রোলের এই দিক পাল্টে যাওয়াকেই বলে Inversion of Control।

খেয়াল রাখো: সম্পর্কটা এভাবে মনে রাখা যায় — IoC একটা principle ("dependency-র ব্যাপারে সিদ্ধান্ত নেওয়ার কন্ট্রোল ক্লাসের বাইরে থাকা উচিত"), আর Dependency Injection হলো সেই principle অর্জন করার (achieve করার) একটা concrete approach বা টেকনিক।

Bean ও IoC Container — পরের লেকচারের প্রিভিউ

এখন পর্যন্ত Main-ই সব dependency তৈরি করছে, সবাইকে একসাথে জুড়ে দিচ্ছে (wiring), এবং পুরো ব্যাপারটা কনফিগার করছে। এখনকার মতো ছোট প্রজেক্টে এটা ঠিকঠাক চলছে, কারণ মাত্র একটা OrderService আর একটা নোটিফিকেশন dependency আছে। কিন্তু বাস্তব প্রজেক্টে যদি শত শত সার্ভিস ক্লাস (UserService, PaymentService...) থাকে, আর তাদের সবার dependency Main-এর ভেতর দিয়েই ম্যানুয়ালি ইনজেক্ট করতে হয়, তাহলে Main নিজেই ভীষণ জটিল ও অগোছালো হয়ে যাবে।

এই সমস্যার উত্তর দেয় Spring Framework। Spring-এর কাছে থাকে একটা IoC Container (Inversion of Control Container) — এটাই আসলে সেই কাজগুলো করে যেগুলো এখন Main ম্যানুয়ালি করছে —

  • প্রয়োজনীয় সব অবজেক্ট নিজে থেকে তৈরি (create) করে
  • সেই অবজেক্টগুলোকে ম্যানেজ (manage) করে — কবে তৈরি হবে, কবে ধ্বংস হবে
  • একটা অবজেক্টের যা যা dependency লাগবে, সেগুলো অন্য অবজেক্টের সাথে নিজে থেকেই কানেক্ট (connect / wire) করে দেয়

Spring-এর ভাষায় এই container-এর হাতে ম্যানেজ হওয়া অবজেক্টগুলোকেই বলা হয় Bean। সহজ কথায়, প্রতিটা Bean আসলে একটা অবজেক্টই — কিন্তু প্রতিটা অবজেক্ট Bean না, শুধু সেই অবজেক্টগুলোই Bean যেগুলোকে IoC Container নিজে তৈরি করে ও ম্যানেজ করে। যখন Spring কোড লেখা শুরু হবে, তখন নিজের হাতে new কীওয়ার্ড লেখা প্রায় দেখাই যাবে না — বেশিরভাগ অবজেক্ট তৈরি ও তাদের মধ্যেকার রিলেশনশিপ ম্যানেজ করার কাজ Spring-এর IoC Container নিজেই সামলে নেবে।

খেয়াল রাখো: এই তিনটা ডায়াগ্রামেই (create, manage, connect) যেখানে এতক্ষণ Main ছিল, পরের লেকচার থেকে সেই জায়গাটা নেবে IoC Container। কীভাবে ঠিক এই container-এর সাথে ইন্টার‍্যাক্ট করতে হয়, সেটাই হবে পরের লেকচারের বিষয়।
অনুশীলন প্রশ্ন
  1. নিজের ভাষায় ব্যাখ্যা করো — tight coupling ও loose coupling-এর মধ্যে মূল পার্থক্য কী, এবং OrderService-এর উদাহরণে সেটা কীভাবে ধরা পড়েছিল?
  2. NotificationService interface-এর একটা নতুন implementation বানাও, যেমন WhatsAppService, যেটা "WhatsApp notification sent" প্রিন্ট করবে। তারপর Main.java-তে কোনো পরিবর্তন না করে শুধু একটা লাইন বদলে সেই নতুন সার্ভিসটা OrderService-এ inject করে দেখাও।
  3. Constructor Injection আর Setter Injection-এর মধ্যে পার্থক্য কী? Bean এবং IoC Container বলতে ঠিক কী বোঝানো হচ্ছে, তা এক-দুই বাক্যে লেখো।
