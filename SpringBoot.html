Lecture 01–04 : Spring পরিচিতি থেকে Dependency Injection ও IoC পর্যন্ত

Client-Server আর্কিটেকচার ও HTTP থেকে শুরু করে Servlet, Spring Framework কেন এলো — তারপর হাতে-কলমে প্রথম Spring Boot অ্যাপ্লিকেশন বানানো, Maven-এর গভীর আলোচনা (pom.xml, dependency, repository, build lifecycle), এবং সবশেষে প্লেইন Java দিয়ে Dependency Injection ও Inversion of Control-এর মূল ধারণা — কনসেপ্ট ব্যাখ্যা, বাস্তব code উদাহরণ এবং অনুশীলন প্রশ্ন সহ।

HTTP ও Servlet প্রথম Spring Boot App Maven Deep-Dive DI ও IoC (Spring ছাড়া) ৪টি লেকচার · ২১টি বিষয়
Lecture 01 — Introduction to Spring Framework
1

ক্লায়েন্ট-সার্ভার আর্কিটেকচার ও HTTP প্রোটোকল

ব্রাউজারে URL (যেমন www.amazon.com) দিলে পেছনে যা ঘটে, সেটাই client-server architecture।

  • Client — যে request পাঠায় (browser, mobile app, React frontend, Postman, এমনকি অন্য একটা server-ও — microservice-এ এক service অন্য service-কে call করলে কলার নিজেও client)।
  • Server — যে request গ্রহণ করে process করে response ফেরত পাঠায়; মূলত একটা কম্পিউটার যেখানে অ্যাপ্লিকেশন hosted থাকে।
Browser (Client) ──── HTTP Request ────► Amazon Server ◄──── HTTP Response ────
  • HTTP (HyperText Transfer Protocol) — client-server-এর মধ্যে common rule book; request/response-এর structure ঠিক করে দেয়।
  • HTTPS — HTTP-র secured ভার্সন; সব ডেটা এনক্রিপ্টেড থাকে, মাঝপথে কেউ শুনে (listen) ফেলতে পারে না। HTTP ডিফল্টে এনক্রিপ্টেড নয়।
HTTP Methods: GET (retrieve), POST (নতুন তথ্য store), PUT (আপডেট), DELETE (মুছে ফেলা), PATCH (নির্দিষ্ট অংশ আপডেট)।

HTTP request-এর ৪টা অংশ:

  • Method — GET/POST/PUT/DELETE/PATCH।
  • URL / Endpoint (Path) — কোন হোস্টের কোন resource-এ request যাচ্ছে (যেমন www.codermy.in/courses)।
  • Headers — key-value মেটাডেটা, যেমন Accept: application/json বা authentication তথ্য।
  • Body — বিস্তারিত ডেটা (যেমন login-এ email/password); সাধারণত POST-জাতীয় call-এ থাকে, GET-এ লাগে না।

HTTP response-এর ৩টা অংশ:

  • Status code — 200 সফল, 201 resource তৈরি হয়েছে, 404 resource পাওয়া যায়নি, 500 internal server error।
  • Headers — response-এর মেটাডেটা।
  • Body — আসল ডেটা।
2

কোর জাভা দিয়ে ওয়েব সার্ভার বানানোর চেষ্টা — সমস্যাগুলো

মূল পার্থক্য: normal java program run হয়ে exit করে যায়, কিন্তু website 24/7 চালু থাকে — কন্টিনিউয়াসলি চলে request-এর জন্য অপেক্ষা করে।
  • java.net প্যাকেজ (Java 1 থেকেই আছে) দিয়ে networking করা যায়।
  • ServerSocket ক্লাস দিয়ে একটা নির্দিষ্ট port-এ (যেমন 8080) incoming request listen করা যায়।
  • Port number লাগে কারণ — একটা কম্পিউটারে একসাথে অনেক অ্যাপ্লিকেশন চলে (WhatsApp, Chrome, Spotify...), port দিয়েই বোঝা যায় কোন request কোন অ্যাপ্লিকেশনের জন্য।
মূল সমস্যা: java.net দিয়ে raw bytes পড়া গেলেও, জাভার কোড HTTP ফরম্যাট বোঝে না — ওর কাছে সেটা শুধুই একটা stream of bytes।

ServerSocket ব্যবহার করলে ম্যানুয়ালি করতে হতো:

  • Input stream read করা (BufferedReader দিয়ে)।
  • Request parse করা — method, endpoint, host আলাদা করে বের করা।
  • if/else দিয়ে endpoint অনুযায়ী সঠিক method call করা (routing)।
  • Method-এর রিটার্ন থেকে HTTP response তৈরি করা।
  • একসাথে একাধিক ইউজার সামলাতে নিজে multi-threading implement করা।

➜ এই বিপুল boilerplate code-ই আসল সমস্যা — প্রতিটা ওয়েব অ্যাপ্লিকেশনে বারবার করতে হতো।

3

Servlet ও Servlet Container — বয়লারপ্লেটের সমাধান

  • Servlet ও Servlet Container — ১৯৯৭ সালে (J2EE-এর অংশ) এলো, java-তে web development-এর প্রথম প্যাকেজ।
  • Servlet — একটা সাধারণ java class, রান হয় Servlet Container-এর ভেতরে।
  • Servlet Container — একেই সাধারণত "server" বলি; জনপ্রিয় হলো Tomcat (আরও আছে Jetty, Undertow)।

Tomcat নিজে করে দেয়:

  • Port ওপেন রাখা ও incoming bytes read করা।
  • Raw bytes-কে HTTP request-এ decode করা।
  • URL অনুযায়ী কোন servlet call হবে ঠিক করা (routing)।
  • Multi-threading handle করা।
  • Servlet-এর response থেকে HTTP response বানিয়ে client-কে ফেরত পাঠানো।
Client ──HTTP Request──► Tomcat (Servlet Container) ──HttpServletRequest──► Servlet Client ◄──HTTP Response── Tomcat (Servlet Container) ◄──HttpServletResponse── Servlet

➜ ডেভেলপারের কাজ শুধু business logic servlet-এর ভেতরে লেখা — port/byte/thread-এর ঝামেলা Tomcat-ই সামলায়।

4

Spring Framework কেন এলো — ইকোসিস্টেম ও কোর্স রোডম্যাপ

  • Servlet দিয়ে অ্যাপ্লিকেশন enterprise-level-এ বড় হলে কোড tightly coupled হয়ে যায় (প্রচুর object আপসে interlinked) — স্কেল করা কঠিন হয়।
  • Spring Framework এলো এই সমস্যা সমাধানে — core concept: Dependency Injection ও Inversion of Control (IoC), যা অ্যাপ্লিকেশনকে loosely coupled করে।
  • Spring শুধু একটা "framework" নয়, একটা পুরো ecosystem — web application ছাড়াও microservices, reactive apps, cloud apps, event-driven system, serverless, batch processing সবই বানানো যায়।
মডিউলকাজ
Spring Coreবেস আইডিওলজি — Dependency Injection, IoC, Beans (বাকি সব module এর উপরেই দাঁড়িয়ে)
Spring MVCWeb application বানানো (ভেতরে servlet-ই ব্যবহার করে)
Spring DataDatabase-এর সাথে অ্যাপ্লিকেশন connect করা
Spring AOPAspect-Oriented Programming
Spring SecurityLogin/authentication ও authorization
Spring Bootউপরের সব module-এর উপর একটা automation/opinionated layer — দ্রুত project setup ও development শুরু করার জন্য
খেয়াল রাখো: Spring Boot, Spring Framework-কে replace করেনি — এটা একটা opinionated system, default configuration ধরে দ্রুত project বুট-আপ করায়। ভেতরে Spring MVC/Data/AOP/Security-র কোর টেকনোলজি একই থাকে।

Database connectivity চেইন:

  • Spring Data JPA — একটা spec/rule book মাত্র।
  • Hibernate — JPA-র আসল implementation।
  • JDBC — Hibernate-এর নিচে থাকে, আগে যা দিয়ে সরাসরি SQL query লিখতে হতো।
Client ──► Spring Boot Application │ (Spring MVC, Spring Security, Spring AOP — সব Spring Core ভিত্তিক) ▼ Spring Data JPA ──► Hibernate ──► JDBC ──► Database
  • Microservices vs Monolithic — Spring module নয়, একটা architecture design।
  • Monolithic — গোটা অ্যাপ্লিকেশন একটাই, সব endpoint handle করে।
  • Microservices — কাজ ভাগ করে একাধিক ছোট service (Order/Payment/User Service), একে অপরকে HTTP call করে কথা বলে।

➜ এই পুরো architecture (Client → Spring Boot → JPA → Hibernate → JDBC → Database) বুঝলেই Java Full Stack Developer — পুরো কোর্সের লক্ষ্য এটাই।

অনুশীলন প্রশ্ন
  1. Client ও Server-এর সংজ্ঞা নিজের ভাষায় লেখো, এবং একটা উদাহরণ দাও যেখানে একটা server নিজেই আরেকটা server-এর client হয়ে যায়।
  2. HTTP request-এর চারটা অংশ কী কী? Servlet Container (যেমন Tomcat) কোন কোন কাজ ডেভেলপারের হাত থেকে সরিয়ে নেয়?
  3. Spring Boot, Spring MVC-কে replace করেনি কেন? এবং Spring Data JPA → Hibernate → JDBC — এই চেইনটা নিজের ভাষায় ব্যাখ্যা করো।
Lecture 02 — প্রথম Spring Boot Application
5

ব্রাউজার থেকে Server পর্যন্ত: Client-Server, IP, Port ও localhost

লক্ষ্য: ব্রাউজারে URL টাইপ করে "Hello World" দেখা। এই লেকচারে client = ব্রাউজার (Chrome), server = নিজের কম্পিউটারে চলা Spring Boot অ্যাপ্লিকেশন।

  • কোনো ওয়েবসাইট (যেমন codermy.in) হিট করলে ব্রাউজার প্রথমে DNS-এর কাছে গিয়ে domain name-এর জন্য IP address বের করে (প্রতিটা ডিভাইসের ইউনিক IP থাকে)।
  • সেই IP address দিয়ে request সার্ভারে পাঠানো হয়।
  • Port number লাগে কারণ — একই IP-তে একসাথে অনেক অ্যাপ্লিকেশন (Chrome, WhatsApp, Spotify, Spring Boot app) চলে; port দিয়ে বোঝা যায় কোন ডেটা কোন অ্যাপ্লিকেশনের।
খেয়াল রাখো: HTTP ডিফল্টে port 80-তে, HTTPS port 443-এ যায়। সার্ভারের ভেতরের অ্যাপ্লিকেশন (Spring Boot) হয়তো 8080-এ চলে — তখন reverse proxy 443/80 থেকে 8080-এ ম্যাপ করে দেয়।
  • localhost / 127.0.0.1 — client ও server একই কম্পিউটার হলে ব্যবহৃত fixed address; মানে "নিজেকেই request পাঠানো"।
  • তাই URL: localhost:8080/hello — 8080 = port, /hello = API endpoint।
  • Client (ব্রাউজার) → DNS দিয়ে হোস্টের IP খোঁজে (localhost-এর ক্ষেত্রে এই ধাপ লাগে না)
  • IP address-এর সাথে port number যুক্ত হয়
  • Request সেই port-এ শোনা (listen) সার্ভারে পৌঁছায়
  • সার্ভার (Spring Boot অ্যাপ্লিকেশন) endpoint অনুযায়ী response ফেরত পাঠায়
6

Spring Initializr দিয়ে প্রথম Spring Boot প্রজেক্ট তৈরি

  • Scratch থেকে web application বানাতে নিজে হাতে করতে হতো — folder structure, configuration, দরকারি dependency ডাউনলোড। এসবের একটাও business logic নয়।
  • Spring Initializr (start.spring.io) — অপশন সিলেক্ট করলেই রেডি-মেড প্রজেক্ট skeleton (zip) দেয়; folder structure, Java/Spring Boot version আগে থেকেই কনফিগার করা থাকে।

Spring Initializr-এ যেসব অপশন সিলেক্ট করা হয়েছে:

  • Project: Maven (Gradle-Groovy বা Gradle-Kotlin এর বদলে) — এটা একটা project management tool, বিস্তারিত পরের লেকচারে
  • Language: Java
  • Spring Boot version: 4.0.6 — সবচেয়ে স্টেবল ও লেটেস্ট ভার্সন বেছে নেওয়া হয়েছে (SNAPSHOT মানে এখনো "work in progress", RC মানে "release candidate" — এই দুটোই এড়িয়ে যাওয়া ভালো)
  • Packaging: Jar (Java Archive) — পুরনো WAR (Web Archive)-এর বদলে, আজকাল Spring Boot অ্যাপ্লিকেশন সাধারণত Jar-ই ব্যবহার করে
  • Configuration: Properties (YAML-এর বদলে)
  • Java version: 21
  • Dependency: Spring Web — এটা যোগ করলে অ্যাপ্লিকেশন RESTful web request handle করতে পারবে এবং by default embedded Apache Tomcat সার্ভার হিসেবে চলে আসবে (আলাদা করে Tomcat ইনস্টল করতে হবে না)

Generate করে zip (নাম demo) unzip করে IntelliJ-তে ওপেন করলে src/main/java/com/example/demo-এর ভেতর মেইন ক্লাস পাওয়া যায়:

DemoApplication.java
package com.example.demo;

import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;

@SpringBootApplication
public class DemoApplication {

    public static void main(String[] args) {
        SpringApplication.run(DemoApplication.class, args);
    }

}
  • public static void main — Java-র সাধারণ entry point।
  • @SpringBootApplication ও SpringApplication.run(...) — এখনো বোঝার দরকার নেই, শুধু মনে রাখো এই এক লাইনই পুরো Spring Boot অ্যাপ্লিকেশন (embedded server-সহ) চালু করে দেয়।
খেয়াল রাখো: এই পর্যায়ে একটাও লাইন business logic লেখা হয়নি — শুধু কনফিগারেশন/স্ট্রাকচার রেডি হয়েছে, সেটাই Spring Boot অটোমেটিক করে দেয়।
7

@RestController ও @GetMapping দিয়ে প্রথম Endpoint লেখা

  • com.example.demo প্যাকেজে নতুন class HelloController — ভেতরে একটা মেথড যা String রিটার্ন করে।
  • Main থেকে manual object বানিয়ে কল করে console-এ print করা যায় — কিন্তু এটা পুরনো Java-র কায়দা, ব্রাউজার থেকে কল করার উপায় নয়।

ব্রাউজার থেকে /hello লিখলেই মেথড অটোমেটিক কল হতে দুটো অ্যানোটেশন লাগে —

  • @RestController — ক্লাসটাকে বলে দেয় এটা একটা "gateway", অর্থাৎ এখানে API endpoint লেখা হবে
  • @GetMapping("hello") — বলে দেয় কোন URL path (GET request) হিট হলে ঠিক এই মেথডটা কল হবে

এভাবে তৈরি হওয়া চূড়ান্ত কোড:

HelloController.java
package com.example.demo;

import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RestController;

@RestController
public class HelloController {

    // "/hello" endpoint হিট হলে এই মেথড কল হবে
    @GetMapping("hello")
    public String hello() {
        return "<h1>Hello World</h1>";
    }

    // মেথডের নাম আর endpoint-এর নাম এক হওয়া বাধ্যতামূলক নয়
    @GetMapping("bye")
    public String greetBye() {
        return "<h1>Bye</h1>";
    }
}
  • মেথডের নাম (hello, greetBye) আর endpoint path (hello, bye) এক হতে হবে — এমন নিয়ম নেই; @GetMapping-এর ভেতরের string-ই path ঠিক করে।
  • Return value-তে সরাসরি <h1> ট্যাগ থাকলে ব্রাউজার সেটাকে HTML হিসেবে render করবে (plain text না)।
খেয়াল রাখো: @RestController/@GetMapping-এর internals এখনো শেখানো হয়নি — এই লেকচারের উদ্দেশ্য শুধু দেখানো Spring Boot দিয়ে কত দ্রুত working endpoint বানানো যায়।
8

অ্যাপ্লিকেশন Run করা, Response দেখা ও পরের ধাপের ইঙ্গিত

  • DemoApplication run করলে console-এ "Tomcat started on port 8080" — Spring Web dependency যোগ করা মাত্র embedded Tomcat অটোমেটিক চালু হয়ে যায়, আলাদা ইনস্টল লাগে না।
  • Endpoint তৈরির আগে localhost:8080/hello হিট করলে Whitelabel Error Page ("no explicit mapping for /error") — সার্ভার চলছে, কিন্তু ওই path-এর mapping নেই।
  • HelloController বানিয়ে rerun করলে ব্রাউজারে "Hello World" দেখা যায় (<h1>-সহ)।

src/main/resources/application.properties-এ server.port সেট করলে Tomcat নতুন port-এ চালু হয়:

application.properties
spring.application.name=demo
server.port=9090
  • পরিবর্তনের পর পুরনো localhost:8080 কাজ করে না — নতুন localhost:9090/hello হিট করতে হয়। বোঝা যায়, port listen করার কাজ Spring Boot অ্যাপ্লিকেশন নয়, embedded Tomcat করে।
  • প্রায় ১০ মিনিটে একটা কাজ করা Spring Boot অ্যাপ্লিকেশন তৈরি — কোনো manual configuration ছাড়াই।
পরের লেকচারের ইঙ্গিত: Spring Initializr-এ বেছে নেওয়া "Maven" একটা project management tool — dependency ও build পরিচালনা করে, গভীর আলোচনা পরের লেকচারে। @RestController/@GetMapping/Tomcat-এর internals-ও পরে ধাপে ধাপে খোলা হবে।
অনুশীলন প্রশ্ন
  1. HelloController-এ নতুন একটা /greet endpoint বানাও যেটা @GetMapping ব্যবহার করে একটা কাস্টম স্ট্রিং (যেমন "Welcome!") রিটার্ন করে।
  2. application.properties-এ server.port পরিবর্তন করে দেখো — পরিবর্তনের পর কেন পুরনো port-এ "this site can't be reached" দেখায়, তা নিজের ভাষায় ব্যাখ্যা করো।
  3. @RestController আর @GetMapping ছাড়া শুধু main মেথড থেকে manual-ভাবে controller-এর মেথড কল করলে কেন সেটা ব্রাউজার থেকে অ্যাক্সেস করা যায় না — এই পার্থক্যটা লিখে ব্যাখ্যা করো।

JAR ফাইল ও Maven কেন দরকার

  • JAR (Java Archive) — অনেক ক্লাস (Order.java, User.java...) কম্পাইল করলে অনেক .class ফাইল হয়; সবগুলো আলাদা শেয়ার করা বাজে পদ্ধতি (ফোল্ডার স্ট্রাকচার নষ্ট/ফাইল মিস হওয়ার ঝুঁকি)।
  • JAR একটা ZIP-এর মতো প্যাকেজ — .class ফাইল, রিসোর্স (image, properties), প্যাকেজ/ফোল্ডার একসাথে প্যাক করে।
  • দুই সুবিধা — নিজের কোড/লাইব্রেরি সহজে শেয়ার করা যায়, এবং অন্যের third-party library-ও JAR হিসেবে নিজের প্রোজেক্টে ব্যবহার করা যায় (যেমন MySQL Connector)।
  • Library — নিজে রান হয় না (main নেই), শুধু ক্লাস/মেথড থাকে যা অন্যে ব্যবহার করে।
  • Application — independently রান করা যায়, ভেতরে main থাকে।
  • কোনো library কোনো application-এর ভেতরে ব্যবহার হলে সেটা ওই application-এর dependency।
খেয়াল রাখো: Library-র JAR-এ external dependency থাকে না — এটা non-executable JAR (dependency তথ্য থাকে pom.xml-এ)। Application (Spring Boot অ্যাপ)-এর JAR সব dependency সহ executable JAR — independently রান করা যায়।
  • Classpath — রান-টাইমে JVM যেখানে ক্লাস খোঁজে; প্রথমে নিজের কোডে, না পেলে dependency-র JAR-এ।
  • Dependency ম্যানুয়ালি গুগল করে ডাউনলোড করা (mysql.com থেকে সরাসরি) ছোট প্রোজেক্টে চলে, কিন্তু বাস্তবে শত শত dependency, version mismatch, আর transitive dependency (এক dependency আরেকটার উপর নির্ভরশীল) সামলানো কঠিন।
  • ➜ এই ঝামেলার সমাধান — Maven।

Maven আসলে কী — একটি Project Management Tool

  • Maven — একটা project management tool, প্রোজেক্ট ম্যানেজমেন্টের ঝামেলা নিজে হ্যান্ডেল করে যাতে ডেভেলপার business logic-এ ফোকাস করতে পারে।
  • Gradle-ও বিকল্প আছে, কিন্তু Maven সবচেয়ে বেশি ব্যবহৃত ও শেখা সহজ।

Maven চারটা কাজ করে —

  • ফোল্ডার স্ট্রাকচার মেইনটেইন করে — টিমের সবাই একই স্ট্যান্ডার্ড ফলো করে।
  • জাভা কোড কম্পাইল করে — এক ক্লিকে পুরো প্রোজেক্ট।
  • JAR ফাইল বানায় (packaging)।
  • প্রয়োজনীয় সব dependency ডাউনলোড করে — transitive dependency সহ, ম্যানুয়াল কাজ নেই।
Build Systemমন্তব্য
IntelliJ-এর নিজস্ব বিল্ড সিস্টেমশুধু IntelliJ ব্যবহারকারীদের জন্যই কাজ করবে, টিমে সবাই ভিন্ন IDE ব্যবহার করলে ফোল্ডার স্ট্রাকচার আলাদা হয়ে যাবে
Mavenযে কোনো IDE (IntelliJ, Eclipse, NetBeans) থেকে একই স্ট্যান্ডার্ড ফলো করা যায়; ওয়াইডলি ইউজড
GradleMaven-এর বিকল্প, একই কাজ করে কিন্তু ভিন্ন সিনট্যাক্স ও ফাইলে (Groovy/Kotlin DSL)

Build system = কোড কীভাবে বিল্ড/কম্পাইল/প্যাকেজ হবে, dependency কীভাবে আসবে — সেই নিয়মকানুন। টিমে একই build system থাকলে কনসিসটেন্সি বজায় থাকে।

Maven প্রজেক্ট ও ফোল্ডার স্ট্রাকচার (IntelliJ)

  • IntelliJ-তে Maven প্রি-ইনস্টলড থাকে — আলাদা ইনস্টল লাগে না।
  • New Project-এ Maven বেছে নিলে groupId/artifactId জিজ্ঞেস করে — এই ডেমো: artifactId MavenDemo, groupId org.example।
  • দুইটা মূল জিনিস — src ফোল্ডার ও pom.xml; বাকি (.idea, .gitignore, .mvn) internal ফাইল, ইগনোর করা যায়।
  • src-এর ভেতরে main (business logic) ও test (JUnit/Mockito টেস্ট)।
  • main-এর ভেতরে java (.java ফাইল) ও resources (non-java, properties/static image)।
ফোল্ডার স্ট্রাকচার (groupId = org.example)
MavenDemo/
├── pom.xml
└── src/
    ├── main/
    │   ├── java/
    │   │   └── org/example/
    │   │       ├── Main.java
    │   │       ├── Demo.java
    │   │       ├── Demo2.java

খেয়াল রাখো: কম্পাইল/রান করলে Maven target ফোল্ডার বানায়, যেখানে classes-এ একই হায়ারার্কি বজায় রেখে .class ফাইল রাখে। target ডিলিট করলেও চিন্তা নেই — আবার build করলেই রিজেনারেট হয়।

IntelliJ-এর Maven প্যানেলে Lifecycle, Plugins, Dependencies ট্যাব থেকে compile/package ফেজ রান করা যায়।

pom.xml — প্রজেক্টের পরিচয়পত্র

pom.xml (Project Object Model XML) — Maven-এর সবচেয়ে গুরুত্বপূর্ণ ফাইল; নাম, ভার্সন, dependency, plugin — প্রোজেক্টের সব তথ্য এখানে।

pom.xml (আসল প্রোজেক্ট থেকে)
<?xml version="1.0" encoding="UTF-8"?>
<project xmlns="http://maven.apache.org/POM/4.0.0"
         xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
         xsi:schemaLocation="http://maven.apache.org/POM/4.0.0 http://maven.apache.org/xsd/maven-4.0.0.xsd">

    <modelVersion>4.0.0</modelVersion>

    <groupId>org.example</groupId>
    <artifactId>MavenDemo</artifactId>
    <version>1.0-SNAPSHOT</version>

    <packaging>jar</packaging>

    <dependencies>
        <dependency>
            <groupId>com.mysql</groupId>
            <artifactId>mysql-connector-j</artifactId>
            <version>9.5.0</version>
            <scope>compile</scope>
        </dependency>

        <dependency>
            <groupId>org.hibernate.orm</groupId>
            <artifactId>hibernate-core</artifactId>
            <version>7.3.6.Final</version>
            <scope>compile</scope>
        </dependency>
    </dependencies>

    <properties>
        <maven.compiler.source>23</maven.compiler.source>
        <maven.compiler.target>23</maven.compiler.target>
        <project.build.sourceEncoding>UTF-8</project.build.sourceEncoding>
    </properties>

</project>
  • রুট ট্যাগ <project>; xmlns/xsi:schemaLocation হলো schema — কোন ট্যাগ বৈধ তা ঠিক করে (মনগড়া ট্যাগ বসালে IntelliJ "invalid context" এরর দেখাবে)।
  • <modelVersion> — pom মডেলের ভার্সন (৪.০.০), Maven সফটওয়্যারের ভার্সন থেকে আলাদা।

GAV (groupId, artifactId, version) — সারা পৃথিবীতে প্রোজেক্টকে ইউনিকলি আইডেন্টিফাই করে:

  • groupId — নিজের ডোমেইন উল্টো করে লেখা কনভেনশন (coderarmy.in → in.coderarmy); না থাকলে org.example।
  • artifactId — প্রোজেক্টের নাম, এখানে MavenDemo।
  • version — যেমন 1.0-SNAPSHOT; "SNAPSHOT" মানে এখনো কাজ চলছে, শেষ হলে স্থায়ী ভার্সন নাম্বার দেওয়া হয়।
  • <properties> — key-value পেয়ার (maven.compiler.source); কাস্টম key বানিয়ে ${key.name} দিয়ে ফাইলে যেকোনো জায়গায় রেফার করা যায়।
  • <packaging> — jar বা war; না লিখলে ডিফল্ট jar।
খেয়াল রাখো: pom.xml-এও ইনহেরিটেন্স আছে — কিছু উল্লেখ না করলে ডিফল্ট parent Super POM (জাভায় কোনো ক্লাস extend না করলে বাই ডিফল্ট Object inherit করার মতো)। নিজের pom + সব parent মিলিয়ে যে pom Maven আসলে ব্যবহার করে, সেটা Effective POM (IntelliJ-এ Show Effective POM)। Spring Boot প্রোজেক্টে parent spring-boot-starter-parent, যার নিজস্ব chain শেষে Super POM-এ পৌঁছায়।

Dependency যোগ করা — Maven Repository ওয়েবসাইট ও Transitive Dependency

  • Dependency-র exact GAV মুখস্থ রাখার দরকার নেই — mvnrepository.com-এ সার্চ করলে সব ভার্সনের Maven স্নিপেট পাওয়া যায়, কপি-পেস্ট করে <dependencies>-এ বসিয়ে দিলেই হয়।
খেয়াল রাখো: একদম latest ভার্সন নেওয়া ভালো প্র্যাকটিস নয় (বাগের সম্ভাবনা বেশি), খুব পুরনোও না — মাঝামাঝি স্টেবল, বহুল-ব্যবহৃত ভার্সন বেছে নেওয়াই ভালো।
  • pom.xml-এ dependency লিখলেই অটো ডাউনলোড হয় না — IntelliJ-তে reload/sync করতে হয়, তখন Maven ডাউনলোড করে External Libraries-এ দেখায়।
  • Transitive dependency — একটা dependency (যেমন mysql-connector-j) চাইলে তার নিজের নির্ভরতাও (Google Protobuf) নিজে থেকে চলে আসে।
  • hibernate-core যোগ করলে আরও গভীর নির্ভরতা (Jakarta, Glassfish, Eclipse প্যাকেজ) টেনে আনে — Maven প্যানেলের Dependencies ট্যাবে পুরো tree দেখা যায়।
ট্যাগমানে
groupId (dependency-র)যে লাইব্রেরি ডাউনলোড করছি তার প্রকাশকের গ্রুপ আইডি, যেমন com.mysql
artifactId (dependency-র)ওই লাইব্রেরির প্রোজেক্ট নাম, যেমন mysql-connector-j
versionকোন ভার্সন লাগবে
scope (ঐচ্ছিক)কোন ফেজে এই dependency লাগবে তা বলে দেয়; ডিফল্ট মান compile

➜ ম্যানুয়ালি করলে যা সময়সাপেক্ষ, তা এখানে dependency-র নাম বসিয়ে সেকেন্ডে হয়ে যায় — এটাই Maven-এর সবচেয়ে বড় সুবিধা।

Local vs Remote Repository — Maven Central ও .m2 ফোল্ডার

Maven দুই ধরনের repository ব্যবহার করে — Maven Central (remote) ও Local Repository; কোম্পানি-নির্দিষ্ট প্রাইভেট রিমোট repository-ও থাকতে পারে।

Repositoryবিবরণ
Maven Centralএকটা বিশাল রিমোট রিপোজিটরি যেখানে হাজার হাজার JAR ফাইল রাখা আছে; Maven ডিফল্টভাবে এখান থেকেই dependency ডাউনলোড করে (Effective POM-এ এর URL declare করা থাকে)
Local Repository (.m2)নিজের কম্পিউটারে একটা হিডেন ফোল্ডার (.m2/repository) — এখানে আগে ডাউনলোড করা সব dependency এবং নিজের বানানো JAR ক্যাশ হয়ে থাকে
Other Remote Repositoryকোম্পানির নিজস্ব প্রাইভেট রিমোট রিপোজিটরি — প্রাইভেট ইন্টারনাল লাইব্রেরি রাখতে, বা সিকিউরিটির জন্য শুধু ট্রায়েড-অ্যান্ড-টেস্টেড আর্টিফ্যাক্ট ব্যবহার করতে

Dependency ডাউনলোডের পুরো ফ্লো এরকম —

  • Maven প্রথমে pom.xml পড়ে দেখে কোন dependency লাগবে
  • প্রথমে চেক করে local repository-তে (.m2/repository) এটা আগে থেকে আছে কিনা
  • লোকালি পেলে সেখান থেকেই ব্যবহার করে নেয় — কোনো ইন্টারনেট লাগে না, তাই দ্রুত হয়
  • লোকালি না পেলে Maven Central (বা override করা থাকলে কোম্পানির নিজস্ব রিমোট রিপোজিটরি) থেকে ডাউনলোড করে
  • ডাউনলোড করার পরে সেটা .m2-তেও কপি রেখে দেয় (cache করে), যাতে পরের বার আর ইন্টারনেট থেকে আনতে না হয়
খেয়াল রাখো: প্রথমবার বিল্ড করলে সময় লাগে (ইন্টারনেট থেকে dependency আসে), পরের বার দ্রুত (local cache থেকে)। <repositories> ট্যাগ দিয়ে কোম্পানির নিজস্ব রিমোট repository override করা যায়।
  • নিজের JAR-এর নামকরণও GAV কনভেনশন মানে — artifactId-version.jar (এখানে MavenDemo-1.0-SNAPSHOT.jar)।
  • .m2-এর ভেতরে ফোল্ডার স্ট্রাকচার — groupId/artifactId/version/artifactId-version.jar।
.m2 local repository — ফোল্ডার স্ট্রাকচার
~/.m2/repository/
└── org/example/MavenDemo/1.0-SNAPSHOT/
    └── MavenDemo-1.0-SNAPSHOT.jar

~/.m2/repository/
└── com/mysql/mysql-connector-j/9.5.0/
    └── mysql-connector-j-9.5.0.jar

Maven Build Lifecycle — Validate থেকে Deploy পর্যন্ত

কোড রান করার মাঝে অনেক অদৃশ্য ফেজ থাকে, Maven সেগুলো সুসংগঠিতভাবে হ্যান্ডেল করে — একে বলে Build Lifecycle, তিন ভাগে ভাগ করা —

Lifecycleফেজ
Clean Lifecycleশুধু clean — একটা মাত্র ফেজ, এটা স্বাধীন
Default Lifecyclevalidate → compile → test → package → verify → install → deploy
Site Lifecycleশুধু site — ডকুমেন্টেশন/রিপোর্ট বানানোর জন্য

Default Lifecycle-এর ফেজ নির্দিষ্ট ক্রমে একের পর এক ঘটে —

  • validate — প্রোজেক্ট স্ট্রাকচার ঠিক আছে কিনা চেক (pom.xml readable কিনা ইত্যাদি)।
  • compile — .java → .class, target/classes-এ রাখে।
  • test — ইউনিট টেস্ট (JUnit/Mockito) রান করে।
  • package — JAR/WAR বানায়, target-এ রাখে।
  • verify — integration testing/code quality চেক (<plugins> দিয়ে বাড়তি চেক যোগ করা যায়)।
  • install — JAR নিজের local repository (.m2)-তে বসায়, অন্য লোকাল প্রোজেক্টও dependency হিসেবে ব্যবহার করতে পারে।
  • deploy — install করা artifact কোম্পানির রিমোট রিপোজিটরিতে আপলোড করে, টিমের সবাই ব্যবহার করতে পারে।
খেয়াল রাখো: ফেজগুলো লিনিয়ার — যেকোনো ফেজে ক্লিক করলে তার আগের সব ফেজ automatically চলে (যেমন package-এ ক্লিক করলে validate→compile→test আগে হয়ে যায়)। deploy মানে Git push নয় — কোম্পানির private remote repository-তে artifact আপলোড।
  • ফেজ IntelliJ Maven প্যানেল থেকে বা টার্মিনাল কমান্ড দিয়ে চালানো যায় (mvn compile, mvn install)।
  • জনপ্রিয় কমান্ড mvn clean install — আগে target মুছে (clean), তারপর validate→...→install (default) — ফ্রেশ JAR local repository-তে বসায়।
টার্মিনাল কমান্ড

  1. একটা library-র JAR আর একটা application-এর executable JAR-এর মধ্যে মূল পার্থক্য কী? Transitive dependency এখানে কীভাবে হ্যান্ডেল হয়?

টাইট কাপলিং সমস্যা — OrderService নিজেই EmailService বানাচ্ছে

  • এই লেকচারে ইচ্ছে করেই Spring ছাড়া প্লেইন Java-তে ছোট কনসোল প্রজেক্ট (CoreDemo) — দেখানোর জন্য যে DI ও IoC Spring-এর নিজস্ব আবিষ্কার নয়, ভালো Java ডিজাইনের নিয়ম, যার উপর Spring দাঁড়িয়ে।
  • OrderService — অর্ডার প্লেস করে; অর্ডার প্লেস হলে নোটিফিকেশন পাঠাতে EmailService লাগে।
  • সবচেয়ে সোজা উপায় — OrderService-এর ভেতরেই সরাসরি new EmailService() লেখা।
শুরুর ডিজাইন (এখনো interface ছাড়া)
public class OrderService {

    // EmailService-এর অবজেক্ট নিজেই বানিয়ে নিচ্ছে
    EmailService emailService = new EmailService();

    public void placeOrder() {
        System.out.println("Order placed");
        // actual business logic..
        emailService.sendNotification();
    }
}

OrderService এখানে EmailService-এর উপর ডিপেন্ডেন্ট — এটাই dependency, এটা নিজে সমস্যা না (বাস্তব প্রজেক্টে শত শত ক্লাস একে অপরের উপর নির্ভর করে)। আসল সমস্যা অন্য জায়গায়:

টাইট কাপলিং (tight coupling) তৈরি হচ্ছে দুইভাবে —

  • OrderService সরাসরি একটা concrete class (EmailService)-এর সাথে বাঁধা পড়ে গেছে, কোনো abstraction / interface ছাড়াই — কাল যদি SMS বা Pop-up নোটিফিকেশন পাঠাতে হয়, তাহলে OrderService-এর ভেতরে ঢুকে কোড পাল্টাতে হবে, যেটা Open-Closed Principle ভাঙে (ক্লাস extend করা যাবে, কিন্তু modify করা উচিত না)।
  • OrderService নিজের dependency নিজেই তৈরি করছে — অর্থাৎ সে অর্ডার ম্যানেজ করার পাশাপাশি নোটিফিকেশন অবজেক্ট বানানোর কাজটাও করছে। এতে Single Responsibility Principle ভাঙে, কারণ একটা ক্লাসের একাধিক কাজ (multiple responsibility) থেকে যাচ্ছে।
খেয়াল রাখো: অবজেক্ট বানানো নিজে কোনো সমস্যা না। সমস্যা হলো — কোথায় বানানো হচ্ছে। OrderService-এর কাজ হওয়া উচিত অর্ডার ম্যানেজ করা, অন্য কোনো ক্লাসের অবজেক্ট বানানো (factory-র কাজ) না।

ইন্টারফেস দিয়ে ধাপ ১ — NotificationService abstraction, তবু আসল সমস্যা রয়েই গেল

Java-নিয়ম: যতটা সম্ভব interface-এর সাথে কোড করা উচিত, concrete class নয়। প্রথম ধাপ — কমন NotificationService interface (Email/SMS/Pop-up সবাই এক ধরনের নোটিফিকেশন পাঠায়)।

NotificationService.java
package in.coderarmy.notification;

public interface NotificationService {
    void sendNotification();
}
  • EmailService এই interface implements করে; নোটিফিকেশন-রিলেটেড সব ক্লাস আলাদা notification প্যাকেজে।
  • OrderService-এর ভ্যারিয়েবল টাইপ এখন concrete class না হয়ে interface।
মাঝামাঝি ধাপ — টাইপ interface, কিন্তু object তৈরি এখনও ভেতরেই
public class OrderService {

    NotificationService notification = new EmailService();

    public void placeOrder() {
        System.out.println("Order placed");
        notification.sendNotification();
    }
}

notification-এর রেফারেন্স টাইপ এখন NotificationService (interface), EmailService নয় — SmsService লিখলেও কম্পাইল/রান হয় (parent interface reference child class object কল করতে পারে, পলিমরফিজম)।

ফাঁদ: ভ্যারিয়েবলের টাইপ interface হলেও, আসল object এখনো OrderService-এর ভেতরেই new EmailService() দিয়ে concrete-ভাবে তৈরি হচ্ছে — টাইট কাপলিং দূর হয়নি, শুধু ডিক্লেয়ারেশন বদলেছে। নতুন টাইপে সুইচ করতে এখনো OrderService-এর কোড এডিট করতে হয়।

package in.coderarmy.notification;

public class FakeEmailService implements NotificationService {

    @Override
    public void sendNotification() {
        System.out.println("Dummy Email sent");
    }

}
┌── EmailService NotificationService (interface) ──┤── SmsService sendNotification() ├── PopUpNotificationService └── FakeEmailService (শুধু টেস্টের জন্য)

OrderService-এর কোনো ধারণা নেই ঠিক কোন implementation আসছে — শুধু জানে NotificationService আছে ও sendNotification() কল করা যাবে। এটাই loose coupling-এর সুবিধা।

19

Main-এ ম্যানুয়াল Dependency Injection — Constructor ও Setter Injection

আসল সমাধান — OrderService নিজে NotificationService তৈরি করবে না, বাইরে থেকে কেউ সেটা পাঠিয়ে দেবে (inject করবে)। constructor-এ শুধু বলে দেয় তার কী চাই — কীভাবে বানানো হবে সেটা তার মাথাব্যথা নয়।

OrderService.java (আসল কোড)
package in.coderarmy;

import in.coderarmy.notification.EmailService;
import in.coderarmy.notification.NotificationService;
import in.coderarmy.notification.PopUpNotificationService;
import in.coderarmy.notification.SmsService;

public class OrderService {

    NotificationService notification;

    public OrderService(NotificationService notification) {
        this.notification = notification;
    }

    public OrderService() {

    }

    public void placeOrder() {
        System.out.println("Order placed");
        // actual business logic..
        notification.sendNotification();
    }

    public void setNotification(NotificationService notification) {
        this.notification = notification;
    }
}

লক্ষ্য করো, OrderService-এ dependency ইনজেক্ট করার দুই রকম রাস্তা রাখা হয়েছে —

  • Constructor Injection — প্যারামিটার-ওয়ালা কনস্ট্রাক্টর দিয়ে, অবজেক্ট তৈরির সময়েই dependency পাস করে দেওয়া।
  • Setter Injection — একটা খালি (no-arg) কনস্ট্রাক্টর দিয়ে আগে অবজেক্ট বানিয়ে, পরে setNotification() মেথড কল করে dependency বসিয়ে দেওয়া।

➜ কে কার dependency, কীভাবে জোড়া লাগবে (wiring) — এখন Main ক্লাসের দায়িত্ব।

Main.java (আসল কোড)
package in.coderarmy;

import in.coderarmy.notification.*;

public class Main {
    public static void main(String[] args) {
        NotificationService notification = new EmailService();
        //OrderService order = new OrderService(notification);
        OrderService order = new OrderService();
        order.setNotification(notification);
        order.placeOrder();
    }
}

// A class should ask what it needs and not
// build everything itself

// IOC --> Inversion of control
  • Main প্রথমে EmailService, তারপর OrderService বানায়, শেষে setNotification() দিয়ে জোড়া লাগায় (constructor injection দিয়েও এক লাইনে করা যেত)।
  • নোটিফিকেশন টাইপ বদলাতে এখন শুধু Main-এর এক লাইন বদলালেই হয় (new EmailService() → new SmsService()) — OrderService-এর কোডে হাত দিতে হয় না।
খেয়াল রাখো: সারমর্ম — "Don't create your own dependency, get your dependency" / "A class should ask what it needs and not build everything itself"। তৃতীয় ধরন Field Injection-ও আছে, কিন্তু প্লেইন Java-তে সরাসরি সম্ভব না — Spring Framework-এই বোঝা যাবে।
20

Inversion of Control (IoC) — কন্ট্রোলের ফ্লো উল্টে যাওয়া

  • অনেকে DI আর IoC মিলিয়ে ফেলে, কিন্তু এরা আলাদা — সম্পর্কিত মাত্র।
  • IoC = একটা principle/আইডিয়া; Dependency Injection = সেই আইডিয়া বাস্তবায়নের টেকনিক।

DI-এর আগে ও পরে "কন্ট্রোল" কোন দিকে বইছিল —

Injection-এর আগে: Main ──creates──► OrderService ──creates──► EmailService (কন্ট্রোল OrderService-এর ভেতরে ছিল) Injection-এর পরে: Main ──creates──► EmailService Main ──creates──► OrderService Main ──provides (EmailService)──► OrderService (কন্ট্রোল এখন বাইরে, Main-এর হাতে)
  • Injection-এর আগে OrderService নিজেই সিদ্ধান্ত নিচ্ছিল কোন EmailService, কীভাবে তৈরি হবে — কন্ট্রোল ছিল ভেতরে (inside)।
  • Injection-এর পর সিদ্ধান্তটা Main-এর হাতে — OrderService শুধু যা পায় তা ব্যবহার করে।
  • কন্ট্রোল inside থেকে outside-এ সরে যাওয়াকেই বলে Inversion of Control।
খেয়াল রাখো: IoC একটা principle ("dependency-র সিদ্ধান্ত ক্লাসের বাইরে থাকা উচিত"), Dependency Injection সেই principle অর্জনের concrete টেকনিক।
21

Bean ও IoC Container — পরের লেকচারের প্রিভিউ

  • এখন পর্যন্ত Main-ই সব dependency তৈরি, wiring, কনফিগারেশন করছে — ছোট প্রজেক্টে ঠিক আছে।
  • বাস্তব প্রজেক্টে শত শত সার্ভিস ক্লাস (UserService, PaymentService...) থাকলে সব Main-এ ম্যানুয়ালি ইনজেক্ট করলে সেটা জটিল/অগোছালো হয়ে যাবে।

Spring Framework-এর IoC Container এই সমস্যার উত্তর — যা এখন Main ম্যানুয়ালি করছে তা নিজে করে —

  • প্রয়োজনীয় সব অবজেক্ট নিজে থেকে তৈরি (create) করে
  • সেই অবজেক্টগুলোকে ম্যানেজ (manage) করে — কবে তৈরি হবে, কবে ধ্বংস হবে
  • একটা অবজেক্টের যা যা dependency লাগবে, সেগুলো অন্য অবজেক্টের সাথে নিজে থেকেই কানেক্ট (connect / wire) করে দেয়
  • Bean — IoC Container-এর হাতে ম্যানেজ হওয়া অবজেক্ট; প্রতিটা Bean একটা অবজেক্ট, কিন্তু প্রতিটা অবজেক্ট Bean না।
  • Spring কোডে নিজের হাতে new লেখা প্রায় দেখা যাবে না — অবজেক্ট তৈরি ও রিলেশনশিপ ম্যানেজ করা IoC Container-ই সামলাবে।
খেয়াল রাখো: এই তিনটা কাজেই (create, manage, connect) যেখানে এতক্ষণ Main ছিল, পরের লেকচার থেকে সেই জায়গাটা নেবে IoC Container। কীভাবে ঠিক এই container-এর সাথে ইন্টার‍্যাক্ট করতে হয়, সেটাই হবে পরের লেকচারের বিষয়।
অনুশীলন প্রশ্ন
  1. নিজের ভাষায় ব্যাখ্যা করো — tight coupling ও loose coupling-এর মধ্যে মূল পার্থক্য কী, এবং OrderService-এর উদাহরণে সেটা কীভাবে ধরা পড়েছিল?
  2. NotificationService interface-এর একটা নতুন implementation বানাও, যেমন WhatsAppService, যেটা "WhatsApp notification sent" প্রিন্ট করবে। তারপর Main.java-তে কোনো পরিবর্তন না করে শুধু একটা লাইন বদলে সেই নতুন সার্ভিসটা OrderService-এ inject করে দেখাও।
  3. Constructor Injection আর Setter Injection-এর মধ্যে পার্থক্য কী? Bean এবং IoC Container বলতে ঠিক কী বোঝানো হচ্ছে, তা এক-দুই বাক্যে লেখো।
